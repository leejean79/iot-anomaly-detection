## 第一点："同步变化"在标准化域比较，在线算子拿不到分母

**裁定：做法甲，在变换域比较。** 标准化是正系数的仿射变换，两边同除以分母即得原不等式，数学上等价；在线算子从标准化轮的原始值自己做 log1p 变换，不需要分母，不改上游；离线与在线同一写法。

做法甲带来一个顺带的简化：变换域不随标准化参数的版本变化，所以零级换版本后不必重新累积十天基线——上一份裁决书里"换版本后重新累积、期间不做现场条件归因"的规定撤销；换版本后只有门槛（参照直方图 P90 减 P10 的宽度）随新参照更新，基线不动。

但变换域的基线暴露了归因优先次序里的一个问题，这里一并更正。基线是平稳日参照期的日内形状；设备发生位置平移式的漂移之后，所有钟点的小时均值相对基线都会偏离，"同步变化"在整个漂移期间对该通道都成立。按交接文档的优先次序（现场条件排在漂移之前），一台正处于漂移状态的设备，只要它某个钟点连续几天有标志，就会被归为"现场条件"而不是"漂移"。这不对：日界已经做出的漂移结论应当压过小时层面的归因。**优先次序改为：质量问题、分布切换、漂移、现场条件、瞬态事件、异常。** 代价是 C 的正午时段若落在 C 的气体漂移期内，会被归为"漂移"而非"现场条件"；判读口径加一条，报告 C 正午各小时的实际归因与原因。这一更正已并入交接文档 1.23 版。

## 第二点：日内基线与小时均值的可执行写法

**裁定：按备案。** 小时均值与基线都按轮合并（变换域值之和除以读数数），基线取冻结所在当地日起十个当地日、第十日末冻结；离线由提取脚本新增变换域的和与读数数两列，请用户在 Mac 上重跑一次提取。

## 第三点：两档节拍触发的时刻

**裁定：按备案。** 小时节拍在小时终点之后一个滑动步（六十秒）触发，日节拍在日界后六十秒触发并排在该日最后一个小时节拍之后，复核紧随日节拍。这一延迟写入交接文档的时延表（验收项四）。

## 第四点：短重放上的现场条件

**裁定：接受事实，报告注明。** 短重放区间内基线尚未冻结，现场条件规则在短重放上没有被实际检验，靠单元测试与全量离线实验覆盖。按做法甲基线不再因版本重置，这一限制只影响短重放。

## 第五点：光照的重估牵涉超越函数

**裁定：按建议。** 光照通道的重估中位数与四分位距在 Java 与 Python 之间按 1.11 版登记的跨语言例外处理，容差 1e-12；其余四个通道逐位相同。适应执行第一批交接文档验收项一"没有超越函数、不设容差"的写法是设计会话的疏漏，已更正为 1.23 版。同一例外也适用于参照直方图的重新冻结（光照的边在 log1p 域）。
