# 裁决补充：检测器改为按论文实现，作者代码只用于数值交叉核对
# （开发设计日志 0.93 版，对 10 月 19 日裁决书第一点的修订）

> 发出方：开发设计会话。接收方：代码开发 agent。
> 依据：《M5b 开工前核对》补充一节（2026 年 10 月 19 日，代码开发 agent 拿到论文第四章原页后的三方对照）。

## 第一节：修订第一点——按论文实现

昨天的裁决是"按作者代码实现"，理由是当时只有作者代码可以逐位核对。现在有了论文第四章原页，代码开发 agent 的三方对照证明作者代码在两处偏离了论文自己的推导：t 统计量的分母用标准差而论文式 4.2 用方差；t 分位数自由度公式的方差比项用的是 F 分位数的平方的倒数而论文式 4.12 用 F 分位数。这两处不是实现细节，它们改变切点表（在置信度零点九九与零点九九九、鲁棒度零点三与零点五下，两千零一十六个窗长里有一千三百多到一千七百多个窗长的切点不同）和检验结论。理论文档第五条决策引用的是论文的形式化保证，保证依附于论文公式而不是代码，所以实现应当跟随论文。裁决改为：**按论文的算法 2、式 4.1、式 4.2 与式 4.12 实现；作者代码只用来交叉核对求根与分位数计算的数值方法。**

论文没有定下的细节，采纳代码开发 agent 的建议并写进报告：两个检验都只在新子窗均值高于历史子窗时报警（论文 4.5.3 节对作者实现的说明，与性能层"退化只有一个方向"的语义一致）；检验顺序按算法 2 先 F 后 t，事件记录先显著的那一个；F 检验的自由度按式 4.7 的公式书写，论文文字与公式的不一致登记为文献勘误；防除零常数按算法 2 取十万分之一、只加在 F 检验上；报警后清空窗口，不把触发元素放回；F 显著而均值未升时不报警、不清空、计数（昨天第二点不变）。

数值核对办法按代码开发 agent 所述：切点表先按作者代码的自由度公式生成一遍，与作者预先算好的切点文件逐窗长一致，以此证明求根与分位数计算正确；再改用式 4.12 生成正式的表，与 Python 的 scipy 在每个窗长上比对。

昨天裁决书第一点末尾关于"论文的保证不能原样引用"的说法随之修订：实现跟随论文公式之后，论文的误报上界在形式上适用；但它的前提是窗内元素独立同分布，我们的主分流不满足，所以平稳流上的实测报警率仍要报告并与上界并排，上界不作为通过门槛。理论线回传第十八条相应改写。

## 第二节：其余各点不变，补两处更正

第三点（默认鲁棒度零点五）不变。代码开发 agent 核实了论文实验确实用过零点一，交接文档的出处成立；但在我们的窗上限两千零一十六之内零点一无解，默认取零点五的理由仍是"让最优切点机制起作用"。

判读口径第二条的起点更正：六台设备的第一个评分窗末在三月二十四日当地十八时三十四分到十九时二十三分之间，攒够三十个元素后最早可能的报警约在二十四日二十三时三十分到二十五日零时三十分；B 与 H 分别从二十六日十五时十二分与二十六日零时三分才开始评分，它们在三月事件尾段的可用部分更短。交接文档第四节第二条据此改写。

## 第三节：判读口径新增第七条——异常不得被确认为漂移

离线实验的数据原本剔除了设备 E 的注入区间。现在增加一遍不剔除的运行，专门回答"持续性核对能否把异常挡在漂移之外"：对 E 的尖峰、阶跃、爬坡、卡死共十四段注入，逐段记录是否出现候选、是否出现确认。理论预期是候选可以出现、确认不应出现（最长注入为六小时爬坡，与 K 等于三十六恰好相等，这一段是边界，如实记录）。这条口径与第四条（C 的日照直射与傍晚气体上升）一起构成持续性核对的反向对照。
