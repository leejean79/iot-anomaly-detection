## 一、一句话结论

集群运行时已从 Java 8 升级到 Java 11，Flink 仍为 1.13.6，Deeplearning4j 1.0.0-M2.1 在真实
TaskManager 上加载成功，**验收项 V-M3-1（兼容性冒烟门禁）已关闭**，M3 阶段可以按原交接文档
继续推进，无需变更 LSTM 自编码器的设计。

## 二、新的运行时基线（设计时请以此为准）

| 项目 | 升级前 | 升级后 |
|---|---|---|
| 集群镜像 | `flink:1.13.6-scala_2.12-java8` | `flink:1.13.6-scala_2.12-java11` |
| 构建目标 | Java 8 | Java 11（`maven.compiler.release=11`） |
| DL4J / ND4J | 1.0.0-beta7（过渡期） | **1.0.0-M2.1**（Java 11 字节码） |
| JavaCPP | 1.5.3 | 1.5.7 |
| Flink / Kafka / Scala | 1.13.6 / 2.6.3 / 2.12 | 完全不变 |
| 构建守卫 | 无 | `requireJavaVersion [11,12)` + `enforceBytecodeVersion maxJdkVersion 11` |

构建守卫的意义是：今后任何依赖若引入高于 Java 11 的字节码，或有人用更高版本 JDK 构建，Maven
会在编译之前直接失败，而不是等到集群上抛 `UnsupportedClassVersionError`。按 Addendum 2 第七节
的约定，出现此类违规时应回报设计会话裁决，不得改用更高 JDK 绕过。

## 四、对 M3 后续设计有约束力的实测事实

这一节是本回报对设计会话最有价值的部分。以下数字均为实测，不是估算。

### 4.1 张量本身很小，内存瓶颈在运行时而非模型

用项目自己的 `LstmAutoEncoder`，以与 TaskManager 相同的堆配置（`-Xms=-Xmx=1.89GB`）跑完整个
隐藏层网格，测得：

| 阶段 | JavaCPP 张量占用 | 进程常驻内存 RSS |
|---|---|---|
| JVM 启动（ND4J 未加载） | 0 | 42 MB |
| 首次建模（触发原生库加载） | 0 | 197 MB |
| hidden=40 训练 10 轮 | 1.91 MB | 1,390 MB |
| hidden=60 训练 10 轮 | 4.13 MB | 2,139 MB |
| hidden=90 训练 10 轮 | 8.07 MB | 2,571 MB |

模型参数量（实测，与解析式吻合）：

| 隐藏层宽度 | LSTM 层参数 | 输出层参数 | 合计 | FP32 占用 |
|---|---|---|---|---|
| 40 | 7,360 | 205 | 7,565 | 29.6 KB |
| 60 | 15,840 | 305 | 16,145 | 63.1 KB |
| 90 | 34,560 | 455 | 35,015 | 136.8 KB |

**结论**：张量数据全程不超过约 10 MB，而进程 RSS 可达 2.5 GB，两者相差两个数量级。因此模型
规模（隐藏层宽度、窗口长度）在当前量级上**不是**内存约束的主要来源；真正吃内存的是原生库映射
（约 155 MB 固定开销）、ND4J 工作区，以及 Java 堆上的对象与垃圾。设计会话若考虑加大网格或
窗口，可以放心按精度需要来定，不必为内存让步；但若考虑**提高并行度或改为并发训练多个模型**，
则必须重新核算，理由见下一条。

### 4.2 内存上限是进程级而非 slot 级

每个 TaskManager 有 4 个 slot，共享同一个 JVM 进程。JavaCPP 的 `maxphysicalbytes` 比对的是
整个进程的 RSS，因此 4 个 slot 的运行时开销会叠加到同一个计数上。当前配置为：进程总量
4,096 MB，`javacpp.maxbytes` 512 MB（约束张量分配），`javacpp.maxphysicalbytes` 3,584 MB
（约束进程 RSS，留 512 MB 余量给容器上限）。

这意味着：**若设计要求 M3 在训练阶段并发训练多个模型（而非当前网格内串行），或把并行度提到
8 以上，需要先重新核算这三个数字。** 当前 `M3Function.trainAndSelect` 在隐藏层网格
{40, 60, 90} 上是串行建模的，每个 slot 同时只存在一个模型，这是当前配置能够安全承载的前提。

### 4.3 实验窗口长度的硬约束

这一条会直接影响 M3 实验方案的设计，请务必注意。

`M2Job` 的预热轮数由 `--calib-days`（默认 7）乘以每日轮数（86400 ÷ 10 秒 = 8,640）得出，即
**每设备 60,480 轮，约 7 天**，且 `syn-submit-m2.sh` 没有覆盖该默认值。在预热期内，所有轮次
都从 `warmup_bypass` 通道流走，M2 不产出任何离群点。

M3 自身的相位参数默认为 `m3-train-days=7`、`m3-earlystop-days=2`、`m3-thresh-days=2`，合计
**11 天**才能走完 COLLECTING 相位进入 ONLINE。

因此：

- 任何**短于 7 天**的重放，M2 通道恒为静默，M3 也仍在采集期，两条检测通道都不会产出结果；
- 若实验需要同时观察 M2 与 M3 的输出，重放窗口应**不短于 11 天**，并预留 M3 进入 ONLINE 后的
  观察段，建议 14 天以上；
- 若只想做功能性冒烟而不在意统计质量，可临时用 `--warmup-rounds 600` 与缩短的 M3 相位参数，
  但这样得到的结果不具备验收效力（`docs/m2_acceptance.md` 第 108 行记录过：小预热会使
  标准化粗糙、离群数虚高至约 110 万，属假象）。

本次单日回归正是撞上了这一约束：57,442 轮分摊到七台活跃设备约 8,206 轮/台，仅为 60,480 门槛
的 13.6%，因此 `m2_gate_admitted=0`。这是设计上的预期行为，不是缺陷。

### 4.4 一处可选的性能优化（仅记录，未实施）

`LstmAutoEncoder.toRnnInput` 采用逐元素 `putScalar` 构造输入张量，每个窗口执行
60 × 5 = 300 次标量写入。实测中 JavaCPP 存活指针数一度达到 71 万个，产生了可观的堆垃圾与
GC 压力。改为整体构造（`Nd4j.create(扁平数组, 形状)` 加 `permute`）可把 300 次调用降为 1 次。

按 `CLAUDE.md` 第三条"外科手术式改动"，此项与本次迁移任务无关，我只记录未改动。是否在后续
性能优化阶段处理，请设计会话裁决；若要做，需配套修改 `toMaskArray` 与相应单元测试。

## 五、遗留项与需要裁决的问题

### 5.1 Java 8 旧 jar 回归尚未执行（低风险）

Addendum 2 验收第 4.2 项要求确认 Java 8 字节码的旧 jar 仍能在 Java 11 运行时上跑通。该项尚未
执行，命令为在 JobManager 容器内提交 Flink 自带的 WordCount 示例。风险很低（Java 11 向后兼容
Java 8 字节码是语言规范保证），但作为验收条目仍应补齐。

### 5.2 M2 离群点数无法做集群级等值比对（已裁决：接受现状）

由于第 4.3 条所述的预热约束，单日窗口下 M2 不产出离群点；而 `docs/m2_acceptance.md` 中记录的
Java 8 基线是 2022 年 3 月整月的数据，不是这一天。因此不存在可供比对的同窗口基线。

用户已裁决**接受现状**，不再为此追加集群运行。理由是：本次迁移改变的是运行时而非算法，算法层
的数值差异若存在，会由 V-M2-1 的等价性测试捕获——那组测试逐滑动步断言 MCOD 与 O(n²) 暴力
对照器的离群点集合完全相等，已在 JDK 11 下随 74 个测试全绿通过。

若设计会话认为论文或验收材料需要一条集群级的端到端等值证据，可随时重放 2022 年 3 月整月
（`--speedup 3600`，约一小时）与 V-M2-4 基线比对：`m2_outliers_total` 1,249,163、
`m2_points_total` 59,378,802、离群率 2.1%、微簇占用率 93.8%。**此事需要设计会话裁决是否进行。**

### 5.3 重放器的注入参数尚未在脚本文档中暴露

`CsvKafkaReplayer` 已支持 `--inject` 与 `--inject-log`（交接文档决策 8 的最小注入模式已交付），
`syn-replay.sh` 通过末尾的参数透传可以传入，但脚本的用法文档中没有给出这两个参数的说明与示例，
容易被遗漏。M3 的注入实验开始前应补上。**是否现在补，请设计会话安排优先级。**

### 5.4 `CLAUDE.md` 的运行时基线条款待补

## 六、迁移过程中暴露并已修复的两类缺陷（供设计会话了解风险面）

这两项都不是 M3 算法逻辑的问题，而是构建与部署层面的问题，记录于此以便今后识别同类风险。

**第一类，原生库的分类器由构建主机决定。** `pom.xml` 原先只对 `nd4j-native` 显式声明了
`linux-x86_64` 分类器，`openblas` 与 `javacpp` 的原生分类器由构建主机的操作系统决定。在 Linux
上构建恰好正确，在 macOS 上构建则产出 macOS 原生库，随后被剔除非 Linux 库的打包规则过滤掉，
最终 jar 中一个都不剩，TaskManager 报 `UnsatisfiedLinkError`。已通过显式声明两个依赖的
`linux-x86_64` 分类器修复。**教训**：跨平台构建原生依赖时，分类器必须显式声明，不能依赖解析
时的主机推断。

**第二类，参数语义的误用。** `javacpp.maxphysicalbytes` 曾按"堆外预算"的思路取值 768 MB，与
`taskmanager.memory.task.off-heap.size` 对齐。但该参数比对的是整个 JVM 进程的 RSS，而
TaskManager 仅完成启动与库加载 RSS 就已是 769 MB，因此该上限在任何情况下都无法满足。已按
进程总量重新取值为 3,584 MB。**教训**：Flink 的 `task.off-heap.size` 只是记账条目，不具备强制
力；真正的约束来自 JavaCPP 的两个上限，且二者语义不同，不可混用。

## 七、给设计会话的行动建议

1. **可以继续 M3 后续设计**，运行时前置条件已解除，LSTM 自编码器的设计无需变更。
2. 设计后续实验方案时，请把第 4.3 条的**窗口长度约束**作为硬约束纳入：观察 M2 与 M3 输出的
   实验，重放窗口不短于 11 天，建议 14 天以上。
3. 若计划提高并行度或改为并发训练多模型，请先与开发 agent 核算第 4.2 条的进程级内存预算。
4. 请就第 5.2、5.3、5.4 三条给出裁决或安排：是否补做 M2 集群级等值比对；何时补齐重放器注入
   参数的文档；`CLAUDE.md` 运行时基线条款的文本。
