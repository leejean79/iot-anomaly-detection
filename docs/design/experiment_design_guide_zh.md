# 实验设计参考：目标、流程、监控数据与教训

版本：2026-10-10。作者：代码开发代理。

本文总结本项目（M1 接入与标准化、M2 点异常通道、M3 上下文通道）从 2026 年 9 月到 10 月各轮实验的设计思路，
供后续模块（例如漂移检测、适应执行）设计实验时参考。全文按「先定问题，再定口径，再定通过条件，然后才运行」
的顺序组织，每一条做法都附有本项目中的实例和出处文件。

## 〇、术语与编号对照

### 0.1 常用术语

| 术语 | 含义 |
| --- | --- |
| 轮 | 一台设备在同一时刻的五个通道读数（温度、湿度、气压、气体、光照）装配成的一条记录。原始数据约每 10 秒一轮，一天约 8,640 轮 |
| 事件时间 / 处理时间 | Flink 术语。事件时间是数据自带的时间戳（2022 年）；处理时间是集群实际执行时的机器时间（2026 年）。重放时两者完全脱钩 |
| 窗长 / 滑动步 | 点通道窗口长 3,600 秒、每 60 秒滑动一次；上下文通道窗口为 60 轮（约 10 分钟），不重叠 |
| 标定（校准） | 用一段被认为正常的数据确定参数。M1 用前 7 天确定标准化参数；M3 用阈值校准期确定告警阈值 |
| 剖面 | 见 0.2 |
| 参照期 | 剖面中「正常」的基准时段。2026-10-06 裁决起为 03-08 至 03-17（M3 的训练集加早停集） |
| 平稳日 | 逐台平稳日：该设备五个通道的偏移绝对值都不超过 0.5 个参照期宽度的日子，用来计算该台的误报率（2026-10-09 裁决起）。机队平稳日：五个通道的「机队中位偏移」都不超过 0.5 的日子，只用于共模比例等机队统计；注入运行按它安排注入日 |
| 机队 | 全部八台设备 A 至 H |
| 共模告警 | 同一小时内告警的设备数达到在场设备数的四分之三（向上取整）的告警，提示是全机队的环境变化，而不是单台故障 |
| 冷启动 | M3 从攒数据、训练到进入在线的过程。训练是同步执行的，会占住该子任务的线程 |
| 代理键 | 为了让八台设备各占一个子任务而构造的分区键，形如 `A#11`，取设备号时去掉 `#` 之后的部分 |
| 复位 | `syn-reset-env.sh`：清空本项目的 Kafka 主题、重启 Flink 容器、核对配置，作为两次运行之间的门槛 |

### 0.2 「剖面」是什么

剖面是 `../../eda/daily_channel_profile.py` 生成的一张表，回答一个问题：**某一天，某台设备某个通道的原始读数，和
「正常时期」相比偏了多少、散了多少。**

计算方法：

1. 对每台设备、每个通道、每一天（UTC），统计原始读数的中位数、P10 和 P90。
2. 对同一设备、同一通道，在参照期内统计中位数和 P10 至 P90 的宽度。
3. 偏移 = （当天中位数 − 参照期中位数）÷ 参照期宽度。0 表示与参照期相同，+1 表示向上偏了一个参照期宽度。
4. 宽度倍数 = 当天 P10–P90 宽度 ÷ 参照期宽度。大于 1 表示当天比参照期散得更开（三月事件中气体通道达到 2 至 3 倍）。
5. 「机队中位偏移」= 当天八台设备偏移的中位数。

剖面的三个用途：

- **判定平稳日**：某台设备五个通道的偏移都在 ±0.5 以内的日子，是这台设备的平稳日，它的误报率只在这些日子上统计。
  五个通道的机队中位偏移都在 ±0.5 以内的日子是机队平稳日，用于共模比例等机队统计；注入运行按它安排注入日。
  注意偏移只看中位数：注入运行中，B、D、H 在自己的平稳日上告警偏多，那些日子气体通道的宽度倍数达到 1.7 至 2.2，
  也就是中位数没动、散布变大，平稳日判据看不见这种变化。
- **解释告警**：把逐日告警率和逐日偏移并排看，就能分辨告警是「环境真的变了」还是「检测器自己在乱报」。
- **检验预言**：三月事件的五条预言，都要拿告警与剖面中的偏移、宽度对照。

一个重要的教训：剖面的结论依赖参照期的选择。B、H 的分析先用 03-17 至 03-24（阈值校准期）作参照，得出「阈值过紧」；
改用 03-08 至 03-17（训练集加早停集）后，平稳日清单变了，这个初判随之撤回。参照期应当选「模型学到的正常」，
而不是一段可能已被事件污染的时段。

### 0.4 重放完整性的七条断言

`../../deploy/scripts/syn-replay-verify.sh` 在每次长运行结束时执行，七条全部通过才认为这次运行的数据可用。

| 断言 | 检查什么 | 为什么需要 |
| --- | --- | --- |
| 一 轮数对账 | M1 输出的总轮数与 EDA 统计相差不超过 0.2% | 证明重放器和 M1 没有丢数据或多数据 |
| 二 零重复 | 同一设备同一时间戳没有重复的轮 | 证明没有重复发送或重复装配 |
| 三 边界对齐 | 最早、最晚一轮落在重放区间的边界附近 | 证明重放区间完整 |
| 四 冻结落第八天 | 每台设备的标准化参数在第 8 天冻结 | 证明预热期长度正确，各次运行可比 |
| 五 零重启 | 作业重启次数为 0 | 重启会让状态回退，结果不再确定 |
| 六 迟到丢弃为零 | 点通道窗口丢弃的迟到数据为 0 | 断言一至五查的是 M1 输出，看不见下游窗口的丢弃（2026-10-03 事故后增加） |
| 七 覆盖末尾 | 每台设备两个通道的最晚输出都在最后一轮之前 3,600 秒以内 | 从结果端确认每台设备都处理到了最后（同上） |

## 一、总体思路

### 1.1 每次实验只回答清楚的问题

每次实验开始前，先写下它要回答的问题，并把问题归入三类之一：

| 类别 | 问题 | 本项目的例子 | 典型证据 |
| --- | --- | --- | --- |
| 正确性 | 系统做的是不是我们以为它在做的事 | 在线 MCOD 与离线参照是否一致；数据有没有丢 | 逐位等值、计数对账、断言 |
| 能力 | 做得好不好 | 正常时误报多少（V-M3-4 误报率）；异常时能否发现（V-M3-5 注入召回） | 误报率、召回、延迟 |
| 代价 | 要付出多少资源和时间 | 训练多久、推理多慢、内存多少（V-M3-6 性能报告） | 时长、时延分位数、内存峰值 |

三类问题有先后顺序：**正确性不成立时，能力和代价的数字都没有意义。** 例如三月至四月运行中 D、G 丢了 61.5 万轮，
这两台的误报率就不能用；注入运行先用七条断言证明数据完整，召回表才可信。

### 1.2 预言要在运行之前登记

对能力类问题，先根据原理写出可以被证伪的预言，再运行，然后逐条判定「成立、不成立、无法判定」。

- 好的预言要写明对象、时段和比较方式。例如「点通道离群率在 23 至 26 日持续高于基线的 2 倍，并逐日跟随气体宽度倍数」。
- 预言不成立本身就是结论。注入运行中「卡死对上下文通道可见」不成立，直接改变了「数据质量场景由哪个通道承担」的判断。
- 预言要在看到数据之前登记，避免看到结果后再调整说法。

### 1.3 通过条件写在执行之前

运行手册里写明「什么结果算通过、什么结果要停下来」。例如注入运行的通过条件是七条断言加两条预验证条件，
任何一条不通过就先诊断，不取消作业、不复位。这样执行的人不需要临场判断，分析的人也不能事后放宽标准。

### 1.4 决定论是最强的工具

本项目的流水线在相同输入下给出相同输出（点通道没有随机性；上下文通道固定随机种子、单线程训练）。因此可以做
「逐位等值」比较：

- 两次运行之间：注入运行与三月至四月运行，A、B、C、F、H 五台的上下文评分逐窗相同，E 的差异全部落在注入区间内。
  这一条同时证明了运行正确、注入只影响了注入的设备和时段。
- 在线与离线之间：M3 训练集逐一相同、早停集误差逐位相同（E、C 等值核验）；点通道在线离群率与离线探针相差不超过
  ±1%（V-M2-5 等值核验）。

当两边不一致时，差异本身就指向缺陷所在。例如 ±1% 比较中八台一致偏低约 6%，每台多出的滑动步数恰好等于该台的
上下文窗口数，直接定位到「上下文快照混入」。

## 二、协作闭环与各环节产物

```
设计会话裁决（目标、参数、通过条件）
   ↓
代码开发代理：改代码与脚本 → 单元测试 → 写运行手册
   ↓
用户执行手册：复位 → 提交 → 重放 → 核验 → 收集 → 推送
   ↓
代码开发代理：核对数据 → 分析 → 报告（结论、证据、待裁决事项）
   ↓
设计会话裁决下一步
```

| 环节 | 产物 | 位置 |
| --- | --- | --- |
| 裁决 | 裁决书、参数书 | 由用户上传 |
| 实现 | 代码、脚本（附五要素）、测试 | `../../src`、`../../deploy/scripts`、`../../eda` |
| 手册 | 逐步命令、期望输出、失败处理 | `docs/*_runbook_zh.md` |
| 运行数据 | 评分、日志、时间线、核验输出 | `docs/<运行名>/` |
| 报告 | 结论、证据、缺陷记录、待裁决事项 | `../reports` |

脚本的「五要素」是：执行环境、调用命令、前置条件、期望产出、失败兜底。手册中的每一步也按这五项写，执行的人
照着做就能判断每一步是否正常。

## 三、实验类型：由小到大的阶梯

| 层级 | 类型 | 回答的问题 | 成本 | 本项目实例 |
| --- | --- | --- | --- | --- |
| 1 | 单元与等价测试 | 算法和状态机在受控输入下是否正确 | 秒级，本地 | `McodEquivalenceTest`、`PmcodM3FlagEquivalenceTest`、`DeviceKeysTest`（V-M2-1 功能正确性、V-M3-2 单元与集成测试） |
| 2 | 离线网格与探针 | 参数取什么值 | 分钟到小时，单机 | R、k 探针（V-M2-3 校准探针表）；隐单元 × 窗长网格（V-M3-3 离线超参数网格） |
| 3 | 冒烟与短重放预验证 | 改动在集群上能否跑通，关键机制是否生效 | 约一小时 | 冷启动探针（每天折合 864 轮，把冷启动压到几分钟）；代理键预验证 |
| 4 | 全量重放（不注入） | 正常数据上的误报与性能 | 数小时 | 三月重跑、三月至四月运行（V-M3-4 误报率、V-M3-6 性能报告） |
| 5 | 注入运行 | 已知异常能否被发现 | 数小时 | 本次注入运行（V-M3-5 注入召回表） |
| 6 | 诊断与取证 | 出了问题之后查明原因 | 视情况 | 迟到丢弃时间线、诊断材料包 |

使用原则：

- **改动先过低层再上高层。** 代理键改动先写单元测试，再做短重放预验证，通过后才做长运行。预验证抓到了
  `PmcodFunction` 把窗口键当设备号的缺陷，避免了一次几小时的无效长运行。
- **短重放用缩小的时间尺度。** 冷启动探针把「每天折合轮数」从 8,640 降到 864，训练在几分钟内触发，用来验证
  检查点、迟到丢弃、子任务分配这类机制问题，不用来看检测效果。
- **能力问题只在全量数据上回答。** 误报率、召回需要足够长的在线时段和真实的环境变化。

## 四、设计一项实验的步骤

### 4.1 写下问题、预言和需要的证据

用一张表把三者对应起来。注入运行的例子：

| 问题 | 预言 | 证据 |
| --- | --- | --- |
| 卡死能被哪个通道发现 | 点通道看不见，上下文通道看得见 | 卡死区间内两个通道的超阈 |
| 爬坡由哪个通道先发现 | 上下文通道先于点通道 | 两个通道的首次检出延迟 |
| 尖峰能否被发现 | 点通道即时可见；一轮尖峰上下文通道可能看不见 | 各档的检出与延迟 |

### 4.2 选数据与时段

**数据分段**要按模型的需要确定，并且各次运行保持一致，结果才可比。三月至四月运行的分段如下：

| 时段 | 用途 |
| --- | --- |
| 03-01 至 03-08 | M1 预热与标准化标定（7 天） |
| 03-08 至 03-15 | M3 训练集（7 天） |
| 03-15 至 03-17 | M3 早停集（2 天） |
| 03-17 至 03-24 | M3 阈值校准期（7 天） |
| 03-24 至 04-30 | 在线；误报率、召回在这一段上评估 |

注意事项：

- **按各设备的可用轮数分段，而不是按日历。** B、H 缺轮较多，进入训练比其他设备晚。
- **标定期不能与要评估的现象重叠。** 阈值校准期 03-17 至 03-24 包含了三月事件的前半段，校准中位数和四分位距被
  抬高，这被登记为「标定污染」。
- **评估时段要排除已知的异常时段。** 误报率只在平稳日上算；H 在 04-01 至 04-04 的停机按已知事件处理。

### 4.3 定义指标与口径

口径要精确到边界。本项目在口径上出过的问题都来自边界：

| 口径要点 | 做法 | 出过的问题 |
| --- | --- | --- |
| 区间开闭 | 统一用左闭右开 `[开始, 结束)` | 召回脚本把恰在零点结束的注入算进了次日，背景比例从 0 变成 7.13% |
| 归属时刻 | 2026-10-09 裁决起只计首次超阈落在注入区间内的响应：点通道看离群轮的时间戳，上下文通道看窗口起点 | 早先的「区间加一个窗长」口径会把注入结束时的跳回算作检出；新口径下，短于一个窗口的尖峰在上下文通道上按构造不可能被计入 |
| 去重 | 点通道只计「到达滑动步」的离群 | 同一轮在一小时内被评估 60 次，不去重会把注入前就存在的离群算作检出 |
| 记录类型 | 只取需要的那类记录（按 `channel` 或 `m2WindowPoints > 0` 过滤） | 监测主题里混有上下文快照，±1% 比较一致偏低约 6% |
| 结束效应 | 区间内与结束后分开统计 | 爬坡结束时数值跳回，点通道的「检出」全部来自这一跳 |

本项目用到的主要指标：

| 指标 | 定义 | 用于 |
| --- | --- | --- |
| 平稳日误报率 | 平稳日上超阈窗口数 ÷ 窗口数 | V-M3-4 误报率 |
| 共模比例 | 告警窗口中属于共模告警的比例 | 区分环境变化与单台误报 |
| 检出 / 首次检出延迟 | 见第 4.3 节表中的口径 | V-M3-5 注入召回表 |
| 偶然检出概率 | 1 − (1 − 背景比例)^窗口数 | 判断检出是否可能只是碰巧 |
| 离群率相对差 | （在线 − 离线参照）÷ 离线参照 | V-M2-5 等值核验，要求不超过 ±1% |
| 时延分位数 | P50、P95、P99、P99.9 | V-M3-6 性能报告 |

### 4.4 设对照

没有对照的数字无法解读。本项目用过的对照：

1. **离线参照**：同一算法在同一输入上离线复算（点通道探针、M3 离线网格），与在线结果比较。
2. **上一次运行**：利用决定论逐窗比较（第 1.4 节）。
3. **背景时段**：同一设备、同一天、注入区间以外的告警比例，作为召回的对照。
4. **基线期**：三月事件分析以 03-19 至 03-22 为基线，「偏高」定义为高于基线均值的 2 倍。
5. **其他设备**：同一天其他设备是否也告警，用来区分单台问题和环境问题（H 在 04-20、04-26 独自偏高，就是这样发现的）。

### 4.5 写通过条件与预案

- **通过条件**：七条断言、预验证条件、±1% 等，写进手册。
- **停止条件**：例如「Kafka 被重建，立即停下上报」「四月没有平稳日，停下来推送报告」。
- **预授权退路**：例如「若训练后的第一个检查点失败，复位后把检查点间隔改为 86,400,000 毫秒重做」，避免为可预见的
  问题再走一轮裁决。

### 4.6 实验参数表

把影响结果的全部参数集中在一张表里，写进手册开头，并在提交作业时打印出来核对（启动横幅）。注入运行的关键参数：

| 参数 | 值 | 核对方式 |
| --- | --- | --- |
| 空闲时限 | 3,600 秒 | 横幅 `Idle timeout: 3600 s` |
| 子任务分配 | A 至 H 对应子任务 0 至 7 | 横幅 `Device subtasks: {...}` |
| M3 分段 | 训练 7 天 / 早停 2 天 / 阈值校准 7 天 | 横幅 `M3 train/es/th: 7d/2d/7d` |
| 检查点 | 间隔 30 秒，超时 120 分钟，容忍 3 次 | 横幅 `Ckpt interval/timeout` |
| JavaCPP 物理内存上限 | 3,900 MB | `syn-tm-recreate.sh` 与复位核对表 |

### 6.2 监控什么

- **作业状态与重启**：时间线每一行都应是 `RUNNING 重启=0`。
- **检查点**：训练期间检查点会挂起，要确认挂起时长小于超时（本次最长 1,627 秒，超时 7,200 秒），并在训练后完成。
- **进入训练与在线的设备数**：两段重放之间必须等到「已进入在线 8 台」。
- **迟到丢弃**：长运行中只要不为 0，就说明有数据被窗口丢弃。
- **内存**：TaskManager 进程内存峰值与 JavaCPP 上限之间的余量。

### 6.3 无人值守

长运行的监测放在 master 的 tmux 会话里（`syn-m3-watch.sh`、`syn-replay.sh`），本地 Mac 睡眠、断网都不影响记录。
本地只在需要时执行 `status` 查看。

### 6.4 计数器对账的写法

能写成等式的检查都写成等式，并让脚本直接打印「闭合」或「不闭合」。注入运行的例子：

```
admitted(3520747) = rounds(4004965) − warmup(483840) − missing(378) = 3520747  → 闭合
warmup：scaler(483840) 与 gate(483840) 一致
```

## 七、运行后的核验与收集

顺序很重要：

1. **排空**：间隔两分钟各读一次计数器，两次相同才说明积压已处理完。
2. **核验**：七条断言（在作业仍在运行时做，断言五需要读作业的重启次数）。
3. **收集**：监测时间线、评分、训练日志、性能、迟到丢弃历史、注入真值。
4. **核对通过条件**：例如预验证条件（子任务分配、训练后检查点）。
5. **分析**：离线探针、±1% 比较、召回表、误报率等只读 Kafka 主题和本地文件的分析。
6. **入库并确认推送成功**。
7. **取消作业、复位**：复位会清空主题，之后无法再取数。

几条规则：

- **先推送，后复位。** 复位之后 Kafka 数据就没有了，master 上的转储目录也会被清理。
- **大文件压缩保留在本地**，直到依赖它的报告被接受。本次监测转储就是靠本地保留的文件完成了修正后的重算。
- **核验输出要存文件**（`tee`），并检查文件不为空。三月至四月运行第一次的核验输出就是空的，收尾时才重做。

## 八、分析与报告

### 8.1 分析顺序

1. **先核对数据完整**：断言、对账、设备覆盖。
2. **再做交叉核对**：与上一次运行逐窗比较，与离线参照比较。
3. **再看能力指标**：误报率、召回、延迟。
4. **最后解释**：结合剖面、其他设备、时段，说明数字为什么是这样。

### 8.2 读数时的自问清单

- 这个数字的分母是什么？里面有没有混入不该算的记录？
- 区间的两端是开还是闭？零点、窗口边界上的记录归哪一边？
- 对照组是什么？背景比例是多少？
- 「检出」是在区间内还是结束后？是持续的还是一闪而过？
- 每个格子有几个样本？一次试验的结果不能当作比率。
- 结论是否依赖参照期、平稳日这类人为选择？换一种合理的选择，结论还成立吗？

### 8.3 报告结构

本项目报告统一用以下结构（例如 `../reports/m3_inject_run_report.md`）：

1. **结论**：编号列出，每条一两句话，附关键数字。
2. **运行有效性**：断言、通过条件、确定性核对。
3. **各项结果**：每节先给表，再给读法，再给判定。
4. **本轮发现并修正的缺陷**：包括分析脚本自己的缺陷，写明影响和修正提交。
5. **请设计会话裁决或知悉的事项**：每条写清楚需要决定什么。

报告中引用验收项编号时，同时写出内容，例如「V-M3-5（注入召回表）」。

## 九、本项目的教训清单

| 现象 | 根因 | 发现方式 | 以后的做法 |
| --- | --- | --- | --- |
| D、G 自 03-25 起没有输出，丢 61.5 万轮 | `withIdleness` 按处理时间判空闲；同步训练卡住一条路径，水位线越过它，积压到达时被窗口当作迟到数据丢弃 | 重启后核查发现迟到丢弃计数不为 0 | 增加断言六（迟到丢弃为零）与断言七（覆盖末尾）；空闲时限改为 3,600 秒；两段重放；一台设备一个子任务 |
| 代理键启用后逐设备半径不生效 | `PmcodFunction` 把窗口键（`F#3`）当作设备号 | 短重放预验证 | 机制改动先做短重放；为每处取设备号的地方写回归测试，并用「去掉修正后测试应失败」核对测试有效 |
| ±1% 比较八台一致偏低约 6% | 监测主题里混入上下文快照，被当作离群率为 0 的滑动步 | 偏差在各设备上完全一致，多出的滑动步数等于上下文窗口数 | 消费共享主题的脚本必须按记录类型过滤；新增输出类型时检查所有下游消费者 |
| 召回背景比例显示 7.13%，实为 0 | 左闭右开区间的结束时刻恰在零点，被算进次日 | 与误报率报告（E 为 0%）对不上 | 日期归属用 `end − 1`；不同报告之间的同类数字要互相核对 |
| B、H「阈值过紧」的初判被撤回 | 预览用了旧参照期，平稳日清单不同 | 按新参照期重跑 | 结论注明依赖的参照期；初步结果明确标为「预览」 |
| 运行手册中的占位符被原样执行 | 手册写了 `<第二步的总轮数>` | 用户执行报错 | 手册中的值都用命令算出来，不留占位符 |
| JavaCPP 上限显示为空 | 镜像里没有 `ps` | 用户反馈 | 检查进程参数时读 `/proc`；检查结果为空时按失败处理 |
| 核对注入时没有输出 | `syn-replay.sh logs` 是 `tail -f`，只显示最后 10 行 | 用户反馈 | 核对历史输出用 `grep` 搜索日志文件 |
| 第一次核验输出为空 | 输出没有正确写入文件 | 收尾时发现 | 每个结果文件写完后检查行数 |
| 拆行的命令报 `$2: unbound variable` | 命令在终端里被拆成两行 | 用户反馈 | 脚本对缺少参数值的情况给出明确报错 |
| 卡死在两个通道上都看不见 | 温度在 10 分钟内本来变化小，平线与正常形状相近 | 注入运行 | 预言要真的去检验；数据质量类问题可能需要在接入层另设检查 |
