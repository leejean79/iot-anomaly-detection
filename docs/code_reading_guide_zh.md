## 一、一页纸概览

**系统做什么。** 八台设备（A 至 H）大约每 10 秒各上报一组读数，每组含五个检测通道（温度、湿度、气压、气体、
光照）以及若干质量通道。系统在 Apache Flink 上实时地把这些读数整理成「采样轮」，做标准化，然后用两种互补的
方法找异常：

| 模块 | 名称 | 看什么 | 方法 | 输出 |
| --- | --- | --- | --- | --- |
| M1 | 接入与标准化 | 数据本身是否完整、可用 | 解析、成轮、稳健标准化（先标定后冻结） | 标准化的轮、逐设备监测快照 |
| M2 | 点异常通道 | 单个时刻的读数组合在近一小时内是否孤立 | pMCOD（基于距离的流式离群检测） | 离群点名单、三路监测信号 |
| M3 | 上下文通道 | 一段时间（10 分钟）的形状是否反常 | 编码器—解码器 LSTM 自编码器的重构误差 | 每窗一条评分 |

**技术栈。** Java 11、Maven、Flink 1.13.6、Kafka 2.6.3、DL4J 1.0.0-M2.1（M3 的神经网络）。三台云主机：master 上是
Kafka、ZooKeeper、Flink JobManager 与 Prometheus；两台 worker 上各一个 Flink TaskManager 与一个 Kafka 节点。

**代码规模。** 主代码约 8,800 行、38 个类，分 4 个包；测试约 3,700 行、24 个测试类。另有约 40 个部署脚本与
十余个 Python 分析脚本。

## 三、贯穿全项目的设计原则（读任何一个文件之前先知道）

1. **事件时间就是数据里的时间。** 每条 Kafka 记录的时间戳是读数自身的时间（`CsvKafkaReplayer` 写入，
   `M2Job.java:259-265` 读出）。所以把三个月数据以 3600 倍速重放，作业看到的时间流与现场实时运行完全一样，结果
   与重放速度无关。这是所有「重放即验收」的前提。
2. **一个作业、算子链内传递，不经 Kafka 中转。** M3 需要 M2 对每一轮的离群判定来净化训练数据，并且三个模块必须
   共用同一条事件时间线（同一个水位线）。拆成三个作业就得经过 Kafka，事件时间的对齐会变复杂。代价是：任一模块阻塞会拖住整个作业
   （见第九节的三起事故）。
3. **先标定、后冻结，不在线自适应。** 标准化参数在前 7 天标定后冻结（`RobustScalerFunction`），M3 模型训练一次
   后冻结。漂移检测与重新标定是将来 M6 模块的职责，现在的代码只留了入口（`RobustScalerFunction.recalibrate`）。
   这样做使每个模块的行为可预期、可复现，也使「漂移」成为可被观测的对象而不是被悄悄吸收掉。
4. **忠实迁移加朴素对照，正确性可证明。** M2 的 MCOD 算法从 pMCOD 的 Scala 源码逐行迁移（`McodCore`），并配一个
   按定义暴力计算的对照器（`NaiveOutlierOracle`），测试要求两者逐窗口的离群点集合完全相等。
5. **在线与离线用同一份实现。** M3 的训练核心 `M3Training` 是纯函数，在线算子 `M3Function` 和离线网格 `M3Grid`
   调用同一份；离线探针 `M2Probe` 复用 `McodCore`。因此「在线结果与离线参照逐位相同」可以作为验收判据
   （E、C 两台已在三月至四月运行中逐位相同）。
6. **一切可计数、可核验。** 每一道过滤都有计数器（Flink 指标），每台设备每分钟有监测快照，每次运行结束有七条
   断言（`syn-replay-verify.sh`）。设计上不允许「静默丢弃」。
7. **已知限制写在代码与文档里。** 例如同步训练的代价、空闲时限 3600 秒在生产环境的副作用，都在相应代码旁注明，
   并说明何时改回。

## 五、按数据流逐站阅读

每一站按「做什么 → 关键位置 → 为什么这样设计 → 读的时候留意 → 对应测试」组织。

### 5.1 数据源：`source` 包

**`CsvKafkaReplayer`**（`source/CsvKafkaReplayer.java`）

- 做什么：读取全部原始 CSV，按事件时间做全局归并，按设备写入固定分区，按倍速节奏放出。
- 关键位置：`main` 在 65 行；文件发现与嗅探在 234、298 行；按时段过滤在 135 行（注意 `row.ts > endSec`，结束时刻
  **包含在内**，两段重放时第一段要用 23:59:59 的秒数作结束）；节奏器 `Pacer` 在 469 行起，空闲压缩在 508 行附近；
  发送在 613 行（记录时间戳 = 数据时间）。
- 为什么：事件时间来自数据而不是处理时间，倍速只影响多快放完，不影响作业看到的时间流。空闲压缩把数据里几天的停机
  压成几秒处理时间，但**不改事件时间戳**，所以停机在作业眼里仍是停机。
- 留意：`--resume` 才会使用断点文件；`--inject-file` 经 `syn-replay.sh` 传入，避免分号被 shell 截断。

**`DevicePartition`**：显式映射 A→0 … H→7。默认哈希会让 A 与 F 撞到同一分区、留一个空分区，所以改为显式。
注意它决定的是 **Kafka 分区**，与 Flink 内部按键分组落到哪个子任务是两回事（后者见 `DeviceKeys`）。

**`Injector`**：四种注入直接改写原始值，因此注入会自然地经过 M1 的标准化，进入 M2、M3 的视角，与真实异常的路径
相同。规格格式见类注释；测试 `InjectorTest`（14 个用例）。

### 5.2 M1：接入与标准化（`m1` 包）

**`RawLineParser`**：不按键分组（畸形行可能取不到设备号）。四类守卫：畸形行、未知传感器、光照 65536（右删失）、
信号强度 0（缺失哨兵）。设计要点是**不静默丢弃**：可识别的读数打上标记照常下发，由下游逐设备计数进入监测快照。

**`Channels`**：五个检测通道的固定顺序（温度、湿度、气压、气体、光照），以及质量通道与未知通道的分类。全项目
所有 `double[5]` 都按这个顺序。

**`RoundAssembler`**（`m1/RoundAssembler.java`）

- 做什么：同一设备、时间戳**精确相等**的读数装成一轮；同轮重复传感器保留首值；事件时间定时器在 ts+30 秒关闭
  这一轮（38 行常量），缺通道的轮带缺失掩码照常输出。
- 关键位置：`processElement` 59 行、`onTimer` 133 行（142 行设设备号，经 `DeviceKeys.deviceOf` 还原）。
- 为什么：数据里一轮的各传感器读数时间戳完全相同，所以用精确相等成轮；30 秒是等待同轮迟到读数的宽限。
- 留意：轮只在 `onTimer` 里发出，Flink 会给它盖上**定时器的时间戳**（轮时间 + 30 秒）。这曾导致一半的轮进不了
  MCOD 状态，修复见下一条。

**事件时间重对齐 `AlignEventTime`**（`m2/M2Job.java:274-297`）

- 做什么：把每一轮的事件时间改回轮自身的时间戳。
- 为什么：上一条的 30 秒偏移使窗口分配所用的事件时间戳（定时器时间）与 MCOD 准入判据所用的轮时间戳（`arrival`）相差 30 秒，在 60 秒滑动步下，
  有一半的轮被计入窗口却从不进入 MCOD 状态（2026-09-18 发现）。代码旁的长注释完整记录了原因，值得细读。
- 留意：这里用 `forMonotonousTimestamps`，同时保留空闲判定 `withIdleness`，时限由 `--idle-wall` 决定（见 5.5）。
- 测试：`M1M2TimestampAlignmentTest`、`PmcodTimestampOffsetTest`。

**`RobustScalerFunction` 与 `ChannelTransform`**

- 做什么：每设备每通道，前 `warmupRounds` 轮（默认 7 天 × 8,640 = 60,480 轮）只收集样本，然后冻结中位数与四分位距，
  此后 xNorm = (x − 中位数) / 四分位距。预热期输出 `warmup=true`，下游一律不处理。
- 关键位置：`processElement` 133 行、`freeze` 197 行、`decideScale` 263/275 行（四分位距过小时旁路缩放）。
- 为什么：中位数与四分位距对离群值稳健；冻结使标准化不吸收漂移。光照通道先做 log1p（`ChannelTransform`），因为
  它乘性重尾、又有 65536 的删失顶格值，不变换会把距离与损失拽飞（M2 收尾诊断的结论）。
- 留意：被删失的光照值不进标定统计；「相对退化防护」默认关闭（`--relative-guard`），代码保留。
- 测试：`ChannelTransformTest`、`RelativeDegeneracyTest`、`M1PipelineTest`。

**`RawCacheFunction`**：每设备缓存最近 1,000 轮原始值；设备缺席超过「1,000 × 10 秒」后返场即标记冷启动。注释里写明
这是实现取舍。冷启动标记一路传到 M2，触发清空该设备的 MCOD 状态。

**重复值游程守卫 `RepeatRunGuard`**（`m1/RepeatRunGuard.java`，开发决策第十条，2026-10-12 加入）

- 做什么：在 `RawCacheFunction` 里，逐设备逐检测通道统计连续完全相同原始读数的游程（以轮计）；游程达到阈值时在
  轮上写 `stuckMask`，监测快照累计 `stuckRounds` 与 `stuckChannelsMask`，指标为 `m1_guard_stuck_runs`（新出现的卡死
  游程数）与 `m1_guard_stuck_rounds`（被打标的轮数）。
- 关键位置：`RepeatRunGuard.update`（计数规则）、`RawCacheFunction.processElement` 末尾（按设备号查阈值）、
  `MonitoringAggregator` 的 `STUCK`/`STUCK_MASK` 两个累积量。
- 为什么：注入运行证明冻结在合理值上的读数对两个检测通道按构造不可见，卡死只能在接入层按「读数不再变化」识别。
- 留意：缺失的通道既不延长也不打断游程；冷启动清零全部游程；阈值由 `--stuck-run-thresholds`（`.env` 的
  `SYN_STUCK_RUN_THRESHOLDS`）给出，取 `eda/repeat_run_lengths.py` 统计的自然最长游程的两倍，不给则守卫关闭。守卫
  只打标与计数，不改变下游检测行为。
- 测试：`RepeatRunGuardTest`（解析、计数规则、原始缓存算子打标、监测快照计数）。

**`MonitoringAggregator` 与 `MonitoringSnapshot`**：每设备每 60 秒一份快照（轮数、不完整轮、畸形、未知传感器、
重复、删失、哨兵、预热、旁路）。同一个 `MonitoringSnapshot` 类也承载 M2 的三路信号（`m2*` 字段，`windowEnd>0`）
与 M3 的重构误差（`m3*` 字段）。区分方法：M1 快照 `windowEnd=0`；M2 快照 `m2WindowPoints>0`；M3 快照 `m3ReconError`
有值。断言七就是按这个规则只取 M2 快照。

**`M1Job`**：已验收的独立 M1 作业。现在跑验收都用 `M2Job`（它内含完整 M1 链），两者不能同时运行。

**`RoundWindow`**：计数滑动窗口的纯库类，按交接文档的要求**故意没有接入**任何作业，读的时候可以跳过。

### 5.3 M2：点异常通道（`m2` 包）

**`M2Gate`**：三道闸。预热轮不进；有缺失通道的轮不进（缺维向量上距离没有定义）；冷启动轮照常进但带标志；光照
删失的轮照常进（65536 经 log1p 后是确定的数，距离有定义）。每条规则都有计数器。类注释末尾记了一处已知简化。

**窗口配置**（`M2Job.java:336-339`）：事件时间滑动窗口，窗长 3,600 秒、滑动 60 秒，**允许迟到为 0**，迟到数据走侧

### 5.4 M3：上下文通道（`m3` 包）

**`M3Function`**（`m3/M3Function.java`）——每台设备一台状态机，状态值存在 99 行的 `statePhase`

- `processElement`（255 行）：更新转发延迟指标，累计轮数，按相位分派。
- **收集**（`handleCollecting`，284 行）：

**`M3Operator`：输出水位线保持**（`m3/M3Operator.java`，补遗四第二节第 3 条）

*设计出发点。* 补遗四之前，训练占住任务线程，训练期间没有元素被处理，也没有水位线被转发，输出顺序天然正确（代价是
全作业停摆）。补遗四之后，训练在训练线程上进行，任务线程照常收元素、推水位线；训练期间到达的轮先进缓冲，训练结束后
再排空评分。于是出现一个新问题：这些评分的事件时间早于此时已经流过的输入水位线。水位线 W 的含义是「此后不会再有
事件时间不大于 W 的记录」；如果算子照常转发输入水位线，再发出更早的评分，下游任何按事件时间工作的算子（将来聚合
模块的事件时间窗口）都会把它们当作迟到记录丢掉——这正是 M2 点通道窗口处 `sideOutputLateData` 统计的那类丢弃，
三月至四月运行丢 615,474 轮就是同一机理。Flink 的 `KeyedProcessFunction` 不能控制水位线，所以必须在算子层改写。

*原理。* 对外发出的水位线取两者的较小值：输入水位线，和「本子任务所有缓冲中最早一轮的记录时间戳减一毫秒」。

- 减一毫秒：水位线 W 宣告「不会再有时间戳 ≤ W 的记录」，缓冲头那一轮的时间戳 T 必须严格大于发出的水位线，所以取 T − 1。
- 取本子任务全部分键的最小值：水位线是按子任务（算子实例）流动的，不分键；一个子任务上可能有多台设备，只能按最早的
  那台保持。代理键使每个子任务只承载一台设备，这个最小值实际上就是该设备的缓冲头。
- 只增不减：Flink 要求水位线单调，所以只在目标值大于已发出的值时才发出。
- 及时释放：缓冲排空的那一刻（发生在处理元素或处理时间定时器里），立即补发被压住的输入水位线，不等下一条水位线到来。
- 记录时间戳的来源：标注轮由 M2 的滑动窗口函数（`PmcodFunction`）以侧输出发出，它的记录时间戳是滑动窗口的最大时间戳
  （窗口末减一毫秒），同一滑动步内的轮共用同一个记录时间戳。`M3Function.bufferRound` 把它连同轮一起存进缓冲
  （`BufferedRound.recordTs`），排空时评分带回这个时间戳，水位线保持也以它为准。

*实现与代码阅读（按调用顺序）。*

1. 挂载：`M2Job.java:390` 用 `transform("M3-LSTM-AE", …, new M3Operator(new M3Function(…)))` 代替原来的 `process(…)`。
   `transform` 允许传入自定义算子，`process` 只能接收函数。
2. 共享的缓冲头表：`M3Function` 里有一张只在任务线程上读写的表 `holdHeadTs`（分键 → 缓冲头的记录时间戳）。
   `bufferRound`（718 行）在缓冲由空变为一轮时写入（736 行）；`drainBatch`（745 行）每排空一批更新为新的缓冲头
   （773 行），排空完毕时删除（766 行）。`earliestBufferedTs`（802 行）返回表里的最小值，没有缓冲时返回 `Long.MAX_VALUE`。
3. 拦截输入水位线：`M3Operator.processWatermark`（60 行）只记下输入水位线（取历史最大值），然后调用 `forwardWatermark`，
   不直接向下游转发。
4. 计算并发出：`forwardWatermark`（79 行）算出 `target = min(输入水位线, 最早缓冲轮 − 1)`（81 行），只在大于已发出值时
   调用父类的 `processWatermark` 发出（82–85 行）。父类方法会同时推进内部的事件时间定时器服务；M3 没有事件时间定时器，
   用保持后的值推进不影响任何行为（定时器服务是父类私有字段，这样写避免触碰 Flink 内部）。
5. 在缓冲变化的路径上及时补发：覆写 `processElement`（66 行）与 `onProcessingTime`（72 行），父类处理完之后都调用一次
   `forwardWatermark`。缓冲的追加与排空只发生在这两条路径里，所以排空完成的同一轮就会发出被压住的水位线。
6. 评分的时间戳：`drainBatch` 在评分前把收集器的时间戳设为该轮的记录时间戳（756 行，`TimestampedCollector.setAbsoluteTimestamp`），
   所以每条评分的时间戳都不小于缓冲头，也就严格大于已发出的水位线。
7. 从检查点恢复：`holdHeadTs` 是内存表，不进检查点；缓冲本身与缓冲头（键控状态 `m3-pending-head-ts`、`m3-pending-size`，
   描述符见 `M3Function.java:131-134`）在检查点里。恢复后，可能在任何元素或定时器到来之前就先收到一条水位线，如果表是空的，
   就会把完整的输入水位线放出去，排空的评分随之迟到。因此 `M3Operator.open`（41 行）用 `applyToAllKeys` 遍历全部分键，
   读出每个分键的缓冲头与占用，经 `M3Function.restoreBuffer`（811 行）回填到表里（48–50 行）。
8. 可观测性：仪表 `m3_watermark_hold_sec`（51 行）给出当前已保持的墙钟秒数；开始保持与释放时各写一行日志
   （「Output watermark held …」「Output watermark hold released after Xs」，87–96 行）。`m3_a4_watch.py` 逐子任务采样
   输入与输出水位线（`currentInputWatermark`、`currentOutputWatermark`），可以直接看到两条线分开又合拢。

*测试。* `M3AsyncTrainingTest.watermarkIsHeldWhileBuffered`（182 行）：训练停在进行中时送入一条越过缓冲头的水位线，断言输出
水位线恰为「缓冲头减一毫秒」；排空后断言恢复为输入水位线；再逐条检查输出流，没有任何评分的时间戳落在它之前已发出的水位线
之后。`restoreResubmitsAndMatchesUninterruptedRun`（223 行）在训练中途做快照、恢复，断言缓冲占用随检查点恢复。

*局限与注意。*

- 目前上下文通道的下游只有 Kafka 写出，写出器用评分记录里的 `windowEnd` 作 Kafka 时间戳，不读记录时间戳，所以这一保持现在
  不改变任何写出内容；它保护的是将来按事件时间消费评分的聚合模块。保持也不延迟评分的写出，只延迟水位线。
- 监测快照经侧输出发出时带的是当前元素或定时器的时间戳，不是该轮的记录时间戳（侧输出的时间戳由 Flink 的上下文决定，函数无法改写）；
  监测写出器同样不读记录时间戳，现在无影响。
- 保持期间，下游若有事件时间窗口，它们的触发会相应推迟，推迟的长度等于缓冲排空完成的时刻，这是正确性的代价。

**分批排空与检查点屏障**（`m3/M3Function.java`，补遗四第二节第 3 条；2026-10-16 全量重放中发现缺陷，2026-10-17 修正）

本节回答两个问题：为什么本项目把检查点时长当作关键指标；「分批排空，批间屏障照常处理」是什么原理。最后说明修正前的代码为什么
没有实现这一意图，以及按 0.86 版裁决第四节所做的修正。缺陷的证据见 `docs/reports/m3_addendum4_full_issues_for_decision.md`。

*检查点的工作方式。* 检查点是给整条流水线拍的一张一致快照：

1. 作业管理器每 30 秒在数据源处向数据流里插入一个特殊标记，叫做屏障（barrier）。
2. 屏障像普通数据一样沿流水线逐级向下游流动，排在它前面的数据先处理，排在它后面的数据后处理。
3. 每个子任务处理到屏障时，把自己当前的状态存下来，并向作业管理器报告这一份已经存好。
4. 所有子任务都报告之后，这次检查点才算完成。「检查点端到端时长」就是从插入屏障到最后一个子任务报告的时间。

关键在于：屏障也排在每个子任务的输入队列里，必须由这个子任务的任务线程亲自取出来处理才算通过。任务线程被别的事情占住时，
屏障只能排队等待。

*本项目为什么特别关注检查点时长。*

- 超时就会重启，重启会产生重复输出。检查点超时是 10 分钟，容忍的失败次数是 0（`M2Job.java:119`、`:264`），一次超时就会让
  作业重启。Kafka 写出是 AT_LEAST_ONCE（至少一次）语义：重启后作业从上一个完成的检查点重新处理，期间已经写出的结果会再写
  一遍。产生的重复记录会让 A4-2（逐位等值）和断言二（零重复）失败，并污染重放基线。
- 一个子任务慢，整个作业都会停。作业使用对齐检查点：一个子任务从多路上游接收数据时，先收到屏障的那几路输入会被暂时阻塞，
  直到其余各路的屏障也到齐。某个子任务迟迟处理不到屏障，它的下游就一直在对齐中等待，上游又因缓冲区写满而产生反压，M1、
  M2 点通道这些与 M3 无关的部分也会被一起拖慢。
- 检查点时长衡量的是任务线程的空闲程度。屏障必须由任务线程处理，所以检查点时长基本上等于任务线程被连续占用的最长时间。
  补遗四之前，训练在任务线程上同步运行，注入运行中同一时段的检查点挂起了 1,627 秒，只能临时把超时调到 60 或 120 分钟。
  A4-1（重放完整性与检查点）用「训练期间每次检查点不超过 30 秒」来验证这个问题已经解决（0.84 版裁决第一节）。

*任务线程的单线程模型。* Flink 的每个子任务只有一个任务线程（邮箱模型），所有工作都在这个线程上排队，一件一件地做：

```
任务线程的循环（简化）：
  反复执行：
    ① 邮箱里有到期的定时器回调 → 执行它（例如 M3Function.onTimer）
    ② 从网络输入队列取下一条 → 是数据就调用 processElement；是屏障就做快照
```

同一时刻只能做一件事。① 里某个回调执行了 30 秒，② 就 30 秒取不到数据，排在队列里的屏障也就等 30 秒。

*「分批排空，批间屏障照常处理」的思路。*

- 问题：训练期间到达的轮都存在缓冲里（全量重放中 G 有 27,965 轮），训练完成后要按顺序全部补做评分，即排空，需要二十多到
  三十多秒的推理。如果在一次回调里一口气排空，任务线程会被连续占用约 30 秒，屏障也就等 30 秒。这相当于把训练堵塞任务线程
  的问题缩小了一号，换了个地方重现。
- 做法：排空切成每批 200 轮（`--drain-batch`，约 0.37 秒）。`drainBatch`（745 行）做完一批后，`advance`（429 行）登记一个
  「1 毫秒之后」的处理时间定时器并立即返回（447 行）。线程回到循环里，先处理网络输入队列中积攒的数据和屏障；1 毫秒后定时器
  到期，再做下一批：

```
时间 →
任务线程：[排空第1批 0.37s][处理输入:5轮+屏障][排空第2批 0.37s][处理输入:5轮][排空第3批]…
                              ↑
                     屏障最多只需等一批，约 0.4 秒
```

  排空的总耗时不变，但被切成了八十多个小段，屏障最多只需等一小段，检查点时长预期在一秒以内。打个比方：一位大客户有 80 笔
  业务，柜员每办一笔就让排队的人先办一下，再回来办下一笔；大客户总共花的时间差不多，后面的人不用干等。
- 顺序不变：排空期间新到的轮不直接评分，而是追加到缓冲尾部（`bufferRound`，718 行），排空总是从缓冲头部取，所以所有轮
  仍然严格按到达顺序评分，与同步训练完全一样。全量重放的 A4-2 全部相同，也证实了这一点。

*修正前的代码为什么没有实现这一意图（缺陷，已修正）。*

问题出在元素处理路径，也就是 `processElement`：

- 排空期间（在线态且缓冲非空），它在追加缓冲之后还调用 `advance`，也就是再排空一批。于是取一条输入就要花 0.37 秒。
  150 倍速下每台设备每秒到达约 15 条，任务线程每秒只能处理约 2.7 条，输入队列越排越长，屏障排在几百条后面轮不到。直到缓冲
  排空，后面的元素改为直接评分（很快），队列瞬间清空，屏障随之通过。所以检查点恰好在排空结束的那一刻完成。用柜台的比方说，
  每当排队的人走到窗口，柜员都要先给大客户再办一笔，排队的人实际上还是在等大客户全部办完。

```
任务线程：[排空第1批][取输入第1条→又排空一批 0.37s][定时器→排空][取输入第2条→又排空一批 0.37s]…
网络输入队列：第3条、第4条……第100条、屏障、第101条……   ← 越积越长
```

- 训练期间，每到达一个元素，`advance` 都会登记一个「当前时刻加 30 秒」的查询定时器，定时器触发时又再登记一个。设计上每台
  设备只有一条查询链，由提交训练时的那次登记开始；实际是每个元素各起一条。单元测试夹具中，
  每秒 15 个元素、训练 30 秒后，同一设备挂着 448 个定时器。训练结束后，这些定时器陆续到期，每个都会再排空一批；每次触发还会
  发出一条训练态状态快照。

全量重放中的表现：超过一秒的六次检查点全部与排空重叠，其中五次在排空结束时完成，最长 22.9 秒；排空中的子任务输入水位线落后
其他子任务 14 至 28 秒（墙钟时间）。单元测试没有发现这个问题，原因是夹具会把同一毫秒的定时器合并，而且不模拟网络输入队列和
屏障。

*修正（2026-10-17，0.86 版裁决第四节）。* `processElement`（358 行）在训练态（385 行）只追加缓冲并调用 `pollTraining` 查询结果槽；
在排空态（389 行起）只追加缓冲。两处都不再调用 `advance`，也不登记定时器。`advance` 只在 `onTimer`（407 行）里调用，于是每台设备
任何时刻只挂一个处理时间定时器：

- 提交训练时登记第一个（557 行）；
- 训练态的回调续登「30 秒之后」（444 行）；
- 排空态的回调续登「1 毫秒之后」（447 行）；
- 排空完毕，链结束。

元素路径收回结果之后，排空从这条链的下一次触发开始，最多晚 30 秒。实时生产中这只多缓冲约三轮，重放中按倍速放大。单元测试
`M3AsyncTrainingTest.oneTimerChainAndElementsDoNotDrain` 断言两件事：训练期间与排空期间夹具中的定时器数始终不超过 1；排空期间
到达的元素只追加、不排空。这个测试在修正前的代码上失败。集群上的验证见运行手册第五节。

*生产环境中的影响。* 实时运行时每台设备每 10 秒到一轮，30 分钟训练只缓冲约 180 轮，一批就排空，影响可以忽略。问题只在重放
中暴露：重放把事件时间压缩了 150 倍，缓冲和排空也随之长了约 150 倍；倍速越高越严重，200 倍时推算约 33 秒，会超过 30 秒上限。

**`M3Training`**（`m3/M3Training.java`，`train` 在 175 行）

- 纯函数：不读写 Flink 状态，不引用 Flink 类型。在线与离线必须调用同一份，否则等值核验无从成立。
- 回调 `EpochListener`（145 行定义，201 行调用）：它不是线程，而是一个回调接口。`train` 在每个 epoch 结束时，在**同一个
  线程**里同步调用一次 `onEpoch`，调用者借此得到每轮的进度：在线算子（`M3Function.java:395-405`）写日志，离线网格
  （`M3Grid.java:321-335`）打印进度与内存。这样做让 `M3Training` 本身不依赖任何日志或输出方式，保持纯函数。整个训练
  （包括这个回调）在补遗四之后都跑在训练执行器的线程上，不再占住 Flink 的任务线程。
- 训练循环：每个 epoch 训练一遍、在早停集上评估；早停集误差改善不足 1e-6 计为无改善，连续 20 个 epoch 无改善即停；
  每个 epoch 末检查线程中断（作业取消时能及时退出）；同时记录最后一次改善的 epoch 与最长平台。
- 测试：`M3TrainingTest`（含中断用例）、`M3EvalBatchTest`。

**`LstmAutoEncoder`**（`m3/LstmAutoEncoder.java`，网络在 `buildModel` 139 行）

- 结构：编码器 LSTM → 取末态 LSTM（整段窗口压成一个 c 维摘要向量）→ 重复向量（复制 L 次）→ 解码器 LSTM → 逐步
  输出层（恒等激活、带掩码的均方误差）。
- 为什么：旧结构每一步输出都能看到同一步的输入，网络可以学成恒等映射，重构任务是退化的（2026-09-22 裁决改正）。
  新结构里解码器只凭摘要向量重构，压缩比是真实的（300 个数压到 60 个）。
- 其他要点：重构目标默认取逆序（`reverseTarget`）；固定随机种子 42；Adam 学习率 0.001；按层二范数梯度裁剪阈值
  39,072——类注释写明这个阈值在实测数据上**从不触发**，是保险而不是约束。窗口长度是结构参数（重复次数），改窗长
  就改了网络。
- 序列化：`serializeModel`/`deserializeModel`（415/438 行），模型参数以字节数组存进检查点状态。

**`WeightedMseLoss`**：缺失与删失的条目权重为零；通道权重可配置；同时保留逐通道误差供马氏距离使用。

**`M3Scorer`**（`calibrate` 51 行，`score` 144 行）：主分 z =（误差 − 中位数）/ 四分位距，阈值 2.22（正态下约等于
3 个标准差）；马氏距离分只报告、不报警。

**`GradientNormRecorder`**：类注释解释了为什么挂在 `onGradientCalculation` 上——挂错钩子会量到 Adam 的更新量而不是
原始梯度。只读，不影响训练结果。

### 5.5 横切机制

**设备代理键 `DeviceKeys`**（`m1/DeviceKeys.java`，2026-10-05）

- 问题：Flink 按「键的哈希 → 键组 → 子任务」分配，八台设备的原始编号在并行度 8 时只落到 5 个子任务上（B、C、E 同在
  子任务 1；D、G 同在 7），同一子任务上的设备只能串行训练。
- 做法：代理键形如 `设备号#序号`，序号由 `generate` 搜索得到，使第 i 台恰好落到子任务 i。整条按键链路的六处分组
  （`M2Job.java` 中的 `DeviceKeys.selector`）统一使用；凡把键当设备号用的地方经 `deviceOf` 还原（`RoundAssembler`、
  `MonitoringAggregator`、`PmcodFunction`）。
- 配置：`SYN_DEVICE_SURROGATE_KEYS`，提交脚本未设时用生成表；表与并行度不匹配时作业拒绝启动
  （`M2Job.java:224-236`）。
- 测试：`DeviceKeysTest`、`DeviceKeysRuntimeTest`（在本地 Flink 运行时核对实际落位）、
  `PmcodM3FlagEquivalenceTest.surrogateKeysKeepDeviceIdsAndPerDeviceRadius`。

**空闲时限**（`M2Job.java:72-78`）：默认 3,600 秒。数据源与 `AlignEventTime` 两处使用。时限太短时，被同步训练阻塞的
路径会被标为空闲，水位线越过它，释放后的积压在允许迟到为 0 的窗口处被全部丢弃（三月至四月运行丢了 615,474 轮）。
注释写明生产环境的副作用（真正离线的设备会拖住全机队窗口一小时）与改回 10 秒的条件。

**检查点**（`M2Job.java:237-245`，`CheckpointCeiling`）：集群没有共享文件系统，用 `JobManagerCheckpointStorage`，状态随
确认消息送回 JobManager。所以真正的上限是 `--checkpoint-max-state-mb` 与集群 `akka.framesize` 中较小的一个；
JobManager 堆内存也要装得下。代码里的默认值（间隔 10 秒、超时 10 分钟、容忍 0 次）与验收运行实际传入的值（30 秒、
120 分钟、3 次）不同，以运行手册为准。

**指标**：Flink 自定义计数器（`m1_*`、`m2_*`、`m3_*`）经 Prometheus 采集。2026-10-02 新增：`m3_inference_latency_ms`
与 `m3_forward_delay_sec` 两个直方图、两个 JavaCPP 内存仪表（`M3Function.java:240-251`）。

### 5.6 M5b：性能层漂移监测（`m5` 包）

**它在数据流里的位置。** M3 的评分输出 `m3Scored`（每台设备每 10 分钟一个评分窗）在写入评分主题的同时，按同一张设备代理键表
再分一次组，进入 `M5bFunction`（`M2Job.java:427-444`，算子名 `M5b-OPTWIN`）。主输出是漂移事件，写 `synergia-drift`；侧输出是
每 60 秒一条的监测快照，写 `synergia-monitoring`。开关 `--m5b-enabled` 默认关闭，关闭时作业拓扑与 M3 收口时完全相同。
M3 的输出水位线保持（补遗四，把 M3 训练移出任务线程后的配套机制）保证评分窗按事件时间有序到达，所以本算子不需要自己排序。

**设计出发点。** 上下文通道的主分如果在一段时间里系统性地升高，说明模型对当前数据的拟合在变差，这就是「性能层漂移」。
检测器按 Tosi 博士论文第四章的最优窗口检测器实现（0.92 版裁决定为按论文、不按作者代码），在检测器后面加一道持续性核对，
把「一次统计显著」与「持续若干小时仍然偏高」区分开：前者只是候选，后者才是确认（交接文档决定四、五，0.94 版第六条）。

**按调用顺序阅读。**

1. `OptWinTables.build`（74-92 行）：作业启动时在 `M5bFunction.open` 里构建，对每个窗长 W（30 至窗上限）求切点、F 临界值与
   t 临界值。切点是论文式 4.1 在整数网格上的最高根（`highestRootCut`，94 行；先以 ⌈W/64⌉ 为步长从高往低粗扫，再逐个细化），
   没有根时取 ⌊W/2⌋，并记 `rootFound = false`。δ′ = δ 的四分之一次方，F 临界值的自由度是（切点 − 1, W − 切点 − 1），t 临界值的
   自由度用式 4.12 在 ν = 切点 / W 处的值（`df`，118-130 行）。分布函数来自 Flink 自带的 Commons Math 3.5。表是常量，不进状态，
   2,016 个窗长的构建在 4 秒以内。鲁棒度 0.1 时在 2,016 以内没有根，切点退化为对半切分（0.92 版第三点）。
2. `OptWinDetector.update`（80 行起）：元素进环形缓冲区（容量为窗上限加一），历史段与新段各自维护增量的和与平方和。窗长不足
   30 时只累积。之后先做 F 检验（方差比，分母加 β = 1e−5），再做韦尔奇 t 检验（样本方差，除以 n − 1）；两者都是单侧的，只在新段
   均值更高时报警。F 显著而均值没有升高时不报警、不清空，只计数（`fWithoutRiseCount`）；两段都是常数时跳过 t 检验并计数
   （`tSkippedConstantCount`）。报警后清空窗口，触发报警的元素不再放回。报警对象 `Alarm` 带上两段的长度、均值、标准差、
   历史段中位数和检验统计量，供持续性核对使用。
3. `DriftGate.onElement`（54 行起）：每个报警都作为候选发出。没有核对在进行时开始一次核对：参照 = 历史段中位数，门限 = 参照
   + ρ × 历史段样本标准差。之后只看候选之后到达的元素（候选之前的元素不混入），凑满 6 个之后，每来一个元素就比较最近 6 个的
   中位数：不高于门限即撤销；一直高于门限、到第 K 个元素时确认。核对进行中又来的候选照常发出（标记 `duringCheck`），但不重启
   核对。K 不得小于 6（构造函数 42 行）。同一元素上若既有核对结论又有新候选，先发核对结论，再发候选。
4. `M5bFunction.processElement`（114 行）与 `feed`（141 行）：十分钟粒度下每个评分窗直接进检测器；小时粒度下按世界协调时整点
   小时累积主分，下一个小时的第一个评分窗到达时以中位数关闭上一个小时，另在该小时起点之后两小时登记一个事件时间定时器作兜底
   （`onTimer` 164-171 行）。分组规则与离线工具 `m5b/prepare_streams.py` 相同。
5. `M5bFunction.onTimer` 的处理时间分支（173-191 行）：每 60 秒发一条快照，`windowEnd = -2`（M3 训练态快照是 −1），字段为当前
   窗长、最近候选与确认的时刻、两项计数（0.94 版第八条）。定时器里只有代理键，设备号由 `DeviceKeys.deviceOf` 还原。

**状态与检查点。** 四个分键状态：`m5b-detector`（窗口内容与增量和）、`m5b-gate`（核对进度与候选之后的六个元素）、
`m5b-hour-bucket`（小时粒度的累积）与 `m5b-marks`（快照用的四个时刻）。检测器窗口最多 2,017 个双精度数，八台设备合计约
130 KB，检查点增量很小；实际体积由 V-M5b-5（逐元素时延、状态体积与检查点增量）的短重放采样给出。交接文档决定五要求设备冷启动
时清空该台状态，本阶段评分流里没有相位回到收集态的信号，所以 `clear()` 只留作接口，类注释里写明了这一点。

**等值的保证方式。** 同一组类有三种用法：在线算子、Java 离线运行器 `OptWinOfflineRunner`、Python 参考实现
`m5b/optwin_offline.py`（读 Java 用 `Double.toString` 写出的同一张常量表，浮点运算顺序相同）。36 种组合上 Java 与 Python 的
事件逐条相同；`M5bFunctionTest` 证明在线算子与离线逻辑逐条相同、中途检查点恢复不改变结果；集群上的在线与离线等值由
`syn-m5b-verify.sh` 的短重放核对（V-M5b-3，离线与在线等值）。

**读的时候留意。** 事件的时刻 `ts` 是评分窗的窗口末（小时粒度是小时起点），单位秒；Kafka 记录时间戳是它乘以 1000。
`magnitude = (新段均值 − 历史段均值) / (历史段标准差 + β)`，只用于报告。

### 5.7 M5a：数据层漂移监测（`m5a` 包）

**它在数据流里的位置。** 数据层有两路输入：标准化轮 `cached`（`RobustScalerFunction` 的输出）与点通道离群记录 `scored`
（`PmcodFunction` 的输出），两路按同一张设备代理键表分组后连接，进入 `M5aFunction`（`M2Job.java:414-431`，算子名
`M5a-DataLayer`）。主输出是数据层事件（状态转移与爆发），写 `synergia-drift`，与性能层事件同一个主题，用 `layer` 字段区分
（`data` 或 `performance`）；侧输出是日记录，写 `synergia-monitoring`，`windowEnd = -3`（性能层快照 −2，M3 训练态 −1）。
开关 `--m5a-enabled` 默认关闭，关闭时作业拓扑与 M5b 收口时相同；上游唯一的改动是 `RobustScalerFunction` 在冻结时多建一份参照
直方图，并挂在冻结后的第一条轮上（`DeviceRound.refHistograms`，只有这一条轮把它写进 `m1-out`）。

**设计出发点。** 性能层看的是模型拟合是否变差，数据层直接看输入分布是否偏离标定周（M5a 交接文档）。三族信号：第一族长记忆，
每个布里斯托当地日对每个通道做一次两样本 KS 检验，参照是标定周样本；第二族是同一天的位置与尺度统计量（偏移、宽度倍数）；
第三族是点通道离群率，按世界协调时整十分钟计，送进与性能层相同的最优窗口检测器，每次报警即一次「爆发」，不经持续性核对
（1.09 版第一节）。长记忆的事件按状态转移发出（1.09 版第二节）：在范围内且 p 小于 α/5 并且 D 大于逐通道 D 零时发 DEVIATE，
已偏离且 D 不大于 D 零时发 RECOVER，不可判的日子不改变状态。D 零为 1.05 版冻结的逐通道值。

   （窗口末 − 滑动步 ≤ 轮时刻 &lt; 窗口末）。
5. `M5aCore.closeBinsUpTo`（215 行）与 `element`（235 行）：事件时间过了十分钟末再加一个滑动步，该十分钟的离群记录都已到达，
   离群率 = 离群轮数 / 入口轮数送进检测器。`element` 先用新元素更新尚未发出的爆发（报警元素起一小时内的离群轮数与峰值、
   包含报警元素的连续非零段长度），再判断它们能否发出：其后一小时之外的元素已到、且连续非零段已经结束。报警元素为零时，持续
   长度取紧挨在它之前的那一段。
6. `M5aFunction`（69、85、92 行）：第一路调用 `onRound`，当日变化时登记日界定时器，并登记该轮所在十分钟的关闭定时器；第二路
   调用 `onOutlier`；`onTimer` 关闭到期的十分钟与当日。定时器里只有代理键，设备号由 `DeviceKeys.deviceOf` 还原。

**状态与检查点。** 一个分键状态 `m5a-core`，即整个 `M5aCore` 对象（Kryo 序列化）：参照直方图（5 × 约 400 个边界与箱频数）、当日
缓冲（`DayBuffer`，每通道最多 8,640 个双精度数，按倍数扩容；带自己的 Kryo 序列化器，检查点只写已用部分，不写扩容留下的空位）、未关闭的十分钟、检测器窗口（最多 2,017 个元素）与尚未发出的爆发。本项目用堆内状态后端，
处理每条轮时不发生序列化；检查点体积随当日缓冲增长，一台设备在当地日末约 0.4 MB，实际值由 V-M5a-5（性能）的短重放采样给出。
`RobustScalerFunction` 新增两个状态 `rs-ref-histograms`、`rs-ref-sent`，重新标定时一并清空。

**等值的保证方式。** `M5aCore` 由在线算子与 Java 离线运行器共用。`M5aCoreTest` 用 `m5a/make_core_fixtures.py` 由 Python 离线
实现（`eda/m5a_extract.py`、`m5b/optwin_offline.py`、`m5a/run_offline.py`）生成的合成数据（跨夏令时切换日，含标定日、缺轮日、
守卫打标日与两段漂移）证明：参照直方图与 numpy 相同，日记录、状态转移与爆发与 Python 相同，在线算子（含中途检查点恢复、
输出经 JSON 往返）与 Java 离线运行逐条相同。集群上的在线与离线等值由短重放核对（V-M5a-3，短重放等值）。

**读的时候留意。** 光照在 log1p 域；Java 的 `Math.log1p` 与 numpy 的 `log1p` 在少数整数输入上相差一个最低有效位，所以与 Python
比较时光照的分位数类字段可差一位，分箱 D 不受影响（参照与当日用同一个变换，相等关系不变）。开发设计日志 1.11 版据此裁定：跨语言
比较对光照经过变换的连续统计量（分位数、偏移、宽度倍数）用 1e-12 的容差，分箱 D、显著性、事件与状态转移逐条相同；集群上 Java
对 Java 的等值一律逐行相同。日记录与状态转移事件的时刻是当地日
结束的世界协调时秒数；爆发的时刻是报警元素的十分钟末。离线运行器以全部设备最后一条轮的时刻减一秒为最终事件时间，在线短重放的
最后几个小时因水位线停在别处而不可比，比较时要截掉。

## 十、已知限制与历史教训（读代码时会看到它们留下的痕迹）

1. **同步训练**（补遗四之前的 `M3Function`）：引发过三起事故——第一次三月运行的 JobManager 内存耗尽与检查点超帧；
   三月重跑的 D、G 缺 10.5 小时；三月至四月运行的 D、G 丢 615,474 轮。补遗四把训练移出任务线程后，临时缓解
   （120 分钟检查点超时、3,600 秒空闲时限、两段重放）撤销；一台设备一个子任务与可中断训练保留。
2. **30 秒事件时间戳偏移**（`AlignEventTime` 的由来）：修复前一半的轮从未进入 MCOD 状态。
3. **风险 R8**（`McodState`）：原文的微簇计数器不在状态里，恢复后编号相撞。
4. **光照通道重尾**（`ChannelTransform`）：log1p 之前，C、D 的点通道过度活跃几乎全部来自光照。
5. **检查点上限是 `akka.framesize`**（`CheckpointCeiling`）：多次排查方向错在 `--checkpoint-max-state-mb`。
6. **窗口键当设备号**（`PmcodFunction.java:100`）：引入代理键时漏改，预验证的断言七抓到。
