## 一、注入策略

### 1.1 为什么要注入

真实数据里没有标注好的异常，无法回答「检测器能抓住多大、什么形状的异常、要多久才抓住」。注入的做法是：在一段
已知平稳的数据上人为加入形状和大小都已知的扰动，并把注入的时间、类型、幅度记成地面真值；运行结束后，用检测
结果对照地面真值，算出每种类型、每档幅度的召回率与检测时延（V-M3-5）。

注入加在**原始读数**上，在重放器发送之前完成。所以注入值会和真实读数一样，依次经过 M1 的成轮与标准化、M2 的
点异常检测、M3 的上下文检测，检测器无从分辨哪些是注入的。这保证了召回结果代表真实路径上的能力。

### 1.2 四种注入类型及其对应的现象

下表中「对 M2」和「对 M3」两列是根据两个通道的工作原理推出的**预期**，正是注入运行要检验的假设，不是已验证的
结论。

| 类型 | 改写方式 | 对应的现象 | 对 M2（点异常通道）的预期 | 对 M3（上下文通道）的预期 |
| --- | --- | --- | --- | --- |
| 尖峰 spike | 原值 + 幅度，持续 1 至 3 轮（1 倍一轮、2 倍两轮、4 倍三轮） | 瞬态故障：电磁干扰、读数跳变、单次误码。属于点异常，不是漂移 | 最适合：注入点在 5 维空间里远离近一小时的其他点，邻居不足即判离群 | 不一定：10 分钟窗口 60 轮里只有 1 至 3 轮异常，重构误差抬升有限，大幅度才可能越过阈值 |
| 阶跃 step | 原值 + 幅度，持续 2 小时 | 突变漂移（均值平移）：传感器重新安装或校准偏差、环境突然改变、偏置型的数据注入攻击 | 只抓开头：阶跃开始后的点找不到旧邻居而被判离群；约一个窗长（1 小时）后窗口里全是平移后的点，彼此互为邻居，离群率回落；阶跃结束时再出现一次反向的短暂离群 | 持续报警：模型冻结在正常水平上，平移后的水平重构不出来，只要平移超出训练分布，2 小时内应持续偏高 |
| 爬坡 ramp | 原值 + 幅度 × 进度，进度在 6 小时内从 0 线性到 1 | 渐变漂移：传感器老化、探头积尘、缓慢的数据注入攻击 | 基本失明：每轮只比上一轮多一点点，近一小时内的点仍连成一片、互为邻居 | 有时延地抓住：偏离随时间增大，误差逐步抬升，越过阈值的时刻取决于幅度 |
| 卡死 stuck | 冻结在注入开始那一刻的原值，持续 2 小时 | 数据质量故障：传感器冻结、网关重复发送旧值。不是漂移，而是正常波动消失（方差塌缩） | 基本失明：冻结值本身是一个正常值，重复出现的点彼此就是邻居；结束时若真实值已偏离冻结值，可能有一次短暂离群 | 不确定，可能最难：若该通道在 10 分钟内本来就变化很小（如温度），一段平直的线看起来也正常 |

几点补充：

1. **尖峰和阶跃在代码里是同一个公式**（原值 + 幅度），区别只在持续时间。持续时间决定了它是点异常还是均值平移。
2. **阶跃最能体现两个通道的分工。**M2 只在变化发生的那一刻报警，随后把新水平当作新常态；M3 的模型冻结在训练
   时的正常状态上，会一直报警。这正是此前三月事件中观察到的「双通道签名」的注入版本。
3. **四种类型都不覆盖「尺度漂移」**，即均值不变、波动幅度变大。三月 22 日至 27 日气体通道的事件就属于这一类，它在
   现有注入里没有对应项，召回结果不能外推到这种现象。

随参数登记的三条预言（2026-10-06《注入实验参数（书面版）》），注入运行据此核对：

1. 卡死对点异常通道不可见（冻结值本身不是离群点），对上下文通道可见（平线是形状异常）。
2. 爬坡在点通道上表现为后段离群率抬升而不是尖峰；在上下文通道上出现得比点通道早。
3. 尖峰在点通道上即时可见；一轮尖峰在上下文通道上可能不可见（被窗口平均）。

### 1.3 幅度怎么定

幅度用「标定期 P10 至 P90 宽度」的倍数表示，取 1、2、4 倍三档（2026-10-02 裁决第六节，10-06 参数书确认），再换算成
原始单位写进规格。

- 标定期取阈值标定期 03-17 至 03-24，与 V-M3-4 报告里的「标定期宽度」是同一把尺子。
- 用宽度的倍数，而不是固定的原始数值，是为了让不同设备、不同通道的注入强度可以比较。
- 换算关系：M1 的标准化用的是四分位距（P25 至 P75）。对近似正态的数据，P10 至 P90 宽度约为四分位距的 1.9 倍。所以
  1 倍宽度的注入，在标准化后大约是 1.9 个单位的偏移；M2 的半径是 1.0，因此即使最小一档的尖峰，也应超出邻居半径。
  这是估算，实际取决于该通道的分布形状。
- 卡死没有幅度。参数书规定卡死在三个不同时刻各做一次，每次 2 小时，值冻结为注入开始时刻的读数。

### 1.4 时间安排的约束

| 约束 | 取值 | 理由 |
| --- | --- | --- |
| 注入设备 | E | 2026-10-02 裁决第六节；E 在四月平稳日的误报率较低（2.39%） |
| 注入通道 | 主通道温度；排得下时在气体通道补做阶跃 2 倍、爬坡 2 倍各一次 | 10-06 参数书 |
| 注入日期 | 四月的平稳日，参照期为 03-08 至 03-17（训练集加早停集） | 背景安静，召回不被真实事件干扰；10-06 裁决第三节把参照期从阈值标定期改为训练集加早停集 |
| 持续时间 | 尖峰 1 至 3 轮，阶跃 2 小时，爬坡 6 小时，卡死 2 小时 | 10-06 参数书 |
| 相邻间隔 | 下限 3,660 秒（点通道窗长 3,600 秒加滑动步 60 秒）；默认 7,200 秒 | 前一次注入的影响完全离开点通道窗口后，再开始下一次，避免互相干扰 |
| 一条注入 | 必须整条落在同一个平稳日里 | 不跨入非平稳日 |

## 二、代码阅读要点

注入涉及四个文件：两个 Java 类（重放器与注入器）、一个 shell 脚本（启动重放）、一个 Python 脚本（生成计划）。

### 2.1 `Injector`（`src/main/java/com/leejean/source/Injector.java`，194 行）

- **规格格式**：`设备:通道:开始秒:持续秒:类型:幅度`，多条用分号分隔。`parse`（149 行）逐条解析，字段数不是 6、数值无法
  解析、类型不在四种之内，都会立即抛出异常，宁可启动失败也不带着错误的规格跑完一整轮。
- **`Spec`**（40 行）：`endTs = startTs + durationSec`，区间是左闭右开 `[开始, 结束)`。
- **`apply`**（95 行）是核心，逐行调用：
  1. 只看设备号和传感器名都匹配、时间落在区间内的行（104-105 行）。
  2. 尖峰与阶跃：原值加幅度（116-121 行）。
  3. 爬坡：`进度 = (当前秒 − 开始秒) / 持续秒`，原值加「幅度 × 进度」（122-125 行）。
  4. 卡死：第一次命中时记下当时的原值，此后每一行都替换成这个值（126-132 行）。冻结值是**按重放顺序**第一条匹配
     行的值，每条规格各记一份。
  5. 每改写一次，`applied` 加一；最后把改写后的值拼回原行。
- **地面真值**（构造函数，66 行）：在注入器创建时就把全部规格写进真值文件（设备、通道、开始、结束、类型、幅度），
  而不是逐行记录。真值描述的是「计划注入了什么」；「实际改写了多少行」看重放结束时打印的 `Injection applied`。
- **留意**：同一行如果同时命中多条规格，会被依次叠加改写。生成脚本保证注入互不重叠，所以正常使用不会出现这种
  情况，但手写规格时要注意。

### 2.2 `CsvKafkaReplayer` 中的接入点（`src/main/java/com/leejean/source/CsvKafkaReplayer.java`）

| 行号 | 做什么 |
| --- | --- |
| 82-98 | 读取 `--inject` 与 `--inject-log`，解析规格并创建注入器；没有规格时注入器为空，后面全部跳过 |
| 116-118 | 启动时打印每条规格，便于核对 |
| 135 | 先按 `--start`/`--end` 过滤时段（结束时刻包含在内） |
| 149-150 | 对通过过滤的每一行调用 `injector.apply`，然后才发送。注入发生在发送之前，所以 Kafka 里存的就是注入后的值 |
| 172 | 结束时关闭真值文件 |
| 192-197 | 打印实际改写的行数；为 0 时警告「没有匹配的行」，通常是设备号、通道名或时间范围写错了 |

### 2.3 `syn-replay.sh` 中的注入参数（`deploy/scripts/syn-replay.sh`）

- 只接受 `--inject-file <规格文件>`（88-92 行），不接受直接传 `--inject`（94-95 行）。原因：重放器的参数会被写进 master
  上的启动脚本再由 bash 执行，规格里的分号会被 bash 当作命令分隔符，只剩第一条注入生效。脚本把文件内容读出后加上
  单引号再传入。
- 真值文件固定写到 master 的 `replay-state/inject-truth.csv`（85、92 行），这个目录挂载在容器外，容器结束后文件仍在。
- **每次启动都会先删除旧的真值文件。**两段重放时，注入规格只能放在包含注入日期的那一段（四月在第二段），否则第二段
  启动时会删掉第一段写下的真值。

### 2.4 `make_injection_specs.py`（`eda/make_injection_specs.py`）

- 读取原始 CSV，取设备 E 温度与气体两个通道在标定期 03-17 至 03-24 的全部读数，算出中位数与 P10 至 P90 宽度。
- 生成计划：温度通道上尖峰、阶跃、爬坡各三档（1、2、4 倍宽度），卡死三次，共 12 条；然后尝试在气体通道上补做阶跃
  2 倍、爬坡 2 倍各一次，排不下只打印说明。
- 尖峰按真实的轮时间戳对齐：从平稳日里的某一轮开始，到第 k+1 轮之前结束，保证恰好覆盖 k 轮（实际轮间隔并不恒为
  10 秒，所以不能简单取 10k 秒）。
- 排程：按「尖峰三档 → 阶跃三档 → 爬坡三档 → 卡死三次 → 气体补做」的顺序，依次排进给定的平稳日。每天从 UTC 零点后
  `--lead-hours` 小时开始；一条注入必须整条落在同一天里；相邻两条之间至少隔 `--gap-sec` 秒。主通道排不下就报错退出。
- 输出两份文件：计划表 CSV（人读）与 `m3_inject_spec.txt`（规格串，交给 `syn-replay.sh --inject-file`）。

### 2.5 测试

`src/test/java/com/leejean/source/InjectorTest.java` 共 14 个用例：解析的正常与异常情形（6 个）、四种类型各自的改写
结果（4 个）、短行原样通过、不同通道不改写、真值文件生成、无真值文件时不崩溃。

## 三、使用方法

注入运行的完整手册见 `docs/m3_inject_runbook_zh.md`。下面是注入这一环节本身的四个步骤。

### 第一步：生成注入计划（本地 Mac）

- **执行环境**：本地 Mac，仓库根目录，Python 3.9 或以上，已安装 `eda/requirements.txt`。
- **调用命令**：
  ```bash
  python3 eda/make_injection_specs.py \
      --data-dir /Users/lijing/Downloads/fwlmb11wni392kodtyljkw4n2/files_csv \
      --days "$DAYS" \
      --out docs/m3_inject_plan.csv
  ```
  必填参数是 `--data-dir`（原始数据目录）、`--days`（四月的平稳日，逗号分隔；`DAYS` 的取法见注入运行手册第一步）、
  `--out`（计划表路径）。可选参数：`--device`（默认 E）、`--channel`（默认 Temperature）、`--extra-channel`（默认 Gas，
  设为空串则不补做）、`--multipliers`（默认 1,2,4）、`--calib-start`/`--calib-end`（默认 03-17 至 03-24）、
  `--gap-sec`（默认 7200，不得小于 3660）、`--lead-hours`（默认 2）。
- **前置条件**：平稳日清单按参照期 03-08 至 03-17 重算（注入运行手册第一步）；原始数据目录可读。
- **期望产出**：终端先打印两个通道标定期的中位数与 P10 至 P90 宽度，再打印计划表（温度 12 条，排得下时另有气体
  2 条）；`docs/m3_inject_plan.csv` 与 `docs/m3_inject_spec.txt` 两个文件生成。
- **常见失败**：
  - 退出码 2：标定期内没有该设备该通道的数据，检查 `--device`、`--channel` 的拼写。
  - 退出码 3：平稳日排不下温度通道的 12 条。按默认参数三天即可排下；平稳日不足时请上报，不要自行减小间隔。
  - 退出码 4：`--gap-sec` 小于 3660，或 `--days` 里有不在四月的日子。

### 第二步：带注入重放（本地 Mac 操作集群）

- **执行环境**：本地 Mac，仓库根目录，经 `fa-master` 别名操作集群。
- **调用命令**（两段重放中的第二段）：
  ```bash
  bash deploy/scripts/syn-replay.sh --speedup 3600 --start 2022-03-27 --end 2022-05-01 --inject-file docs/m3_inject_spec.txt
  bash deploy/scripts/syn-replay.sh logs
  ```
- **前置条件**：作业已提交并处于运行状态；第一段重放已放完，并且八台设备都已进入在线。
- **期望产出**：日志开头打印 `Injection: 12 spec(s)`（有气体补做时为 14）及每条规格；结束时打印
  `Injection applied: <行数>`，行数应大于 0；master 上生成 `/opt/fa-iforest/replay-state/inject-truth.csv`（表头一行加
  每条规格一行）。
- **常见失败**：结束时出现 `[WARN] No rows matched injection specs`，说明没有任何行被改写，通常是通道名与原始数据中
  的写法不一致，或注入时间不在本段的时间范围内。这种情况下这一轮注入实验无效，需要先查明原因。

### 第三步：收集地面真值

- **执行环境**：本地 Mac，仓库根目录。
- **调用命令**：运行结束后的收集脚本会一并拉回真值文件：
  ```bash
  bash deploy/scripts/syn-m3-march-collect.sh --out-dir docs/m3_inject --since "$SINCE"
  ```
- **期望产出**：`docs/m3_inject/inject-truth.csv` 存在，`collect_summary.txt` 中「注入真值行数（含表头）」为 13 或 15。
- **常见失败**：提示「master 上没有 inject-truth.csv」，说明重放没有带 `--inject-file`，或真值文件已被后来的一次重放
  启动删掉了。

### 第四步：召回表（V-M3-5）

- **执行环境**：本地 Mac，仓库根目录，Python 3.9 或以上，已安装 matplotlib。
- **调用命令**：
  ```bash
  python3 deploy/scripts/m3_injection_recall.py --truth docs/m3_inject/inject-truth.csv \
      --scores docs/m3_inject/scores.jsonl --plan docs/m3_inject_plan.csv --out-dir docs/m3_inject/recall
  ```
- **口径**：检出指注入区间内（含其后一个窗长）出现超阈；首次检出延迟为首个超阈窗口末减注入开始时刻。点通道只计
  在到达滑动步被判离群的轮，窗长 3,600 秒；上下文通道窗长 600 秒。另按注入日其余时段的超阈比例给出偶然检出概率。
- **前置条件**：第三步已拉回真值文件与评分转储。
- **期望产出**：`docs/m3_inject/recall/` 下有 `recall.md`（召回表、背景、三条预言的核对数据）、`recall.csv`、
  每条注入一幅响应图 `figs/inject_NN_<类型>.png`。
- **常见失败**：退出码 2 表示真值或评分文件不存在；退出码 3 表示评分里没有注入设备的上下文通道记录。

## 四、已确认的事项

此前待设计会话确认的两项，已由 2026-10-06《注入实验参数（书面版）》确认：

1. **卡死**：在三个不同时刻各做一次，每次 2 小时，值冻结为注入开始时刻的读数。
2. **间隔下限中的「窗长」**：指点异常通道的窗长 3,600 秒，下限为 3,660 秒；默认间隔 7,200 秒。
