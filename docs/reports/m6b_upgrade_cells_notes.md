## 二、由我选定的写法（请设计会话确认）

1. **格的判定次序。**先判二级，再判「只有性能层持续」，再判「两层同报」，再判「零级之后同一通道新持续段」，其余为零级。一条命令只命中一个格。
2. **「两层同报」的两种情形。**裁决第四问确认沿用现有写法，即「同一天性能层持续且该通道数据层同日偏离」。现有代码里，命令依据写「两层同日同报」的情形是：数据层当日偏离、前一日没有偏离、性能层在决定时刻处于确认状态。我把下面两种情形都算作两层同报：
   - 某个数据层触发通道的形态为「两层同日同报」；
   - 性能层持续，即确认跨过日界，同时有数据层触发通道（这时该通道当日一定偏离）。
   第二种情形下，数据层也可能已经连续偏离两日。如果设计会话认为这种情形应按「只有数据层持续」处理，改动只在 `cell` 的一行。
3. **「零级之后同一通道新持续段」的段起点。**段起点取从当日向前连续偏离的第一天，但不早于零级生效的当地日，因为换版本时数据层状态已清零。段起点落在「零级生效时刻」到「生效后七个当地日」之间，记为命中。只有零级的触发通道算「同一通道」，零级之后另一个通道的持续段不算。
4. **二级的判定。**触发含性能层，且性能层当前确认段的开始时刻落在「最近一条一级的重训完成时刻」到「完成后七个当地日」之间。确认段的开始时刻取聚合模块性能层跟踪的确认起点。
5. **二级的重训完成时刻。**裁决第一问只给了一级。二级回到收集态、按首次训练的数据段从头训练，所以我取「生效时刻加冷启动三段的天数」：作业默认为训练七天、早停两天、标定七天，合计十六天。二级的冷却期为此后七个当地日。
6. **天数的计法。**N 与二级的收集长度按秒计，与上下文模块一致（N 乘以 86,400 秒）。K_up 与冷却期按当地日计，与零级原有的冷却期一致。
7. **聚合模块的性能层跟踪不随模型代数清空。**性能层（M5b）在模型代数改变时清空该台的检测器；聚合模块自己的性能层跟踪仍按收到的确认与元素推进，切换之前的确认段要等新模型的评分低于门限才回落。二级要求确认段开始于重训完成之后，所以切换之前的确认段不会触发二级。
8. **Python 参考实现未改动。**升级格关闭时，Java 与 `m7/decide.py` 照旧逐条相同。升级格打开后的 Python 对照尚未编写；如果验收需要，请设计会话示下。

## 三、一级默认参数的改动

- 按 1.40 版裁决（一级默认参数选定：训练窗口取生效之后、N 三天、冷启动）与 1.41 版裁决第四节，作业参数 `--m3-retrain-days` 的默认值由七改为三，`--m3-retrain-side` 由 before 改为 after，`--m3-retrain-warm` 由 true 改为 false。

## 四、按 1.43 与 1.44 版裁决补做的部分（2026 年 11 月 13 日）

- **第二节第 7 条改写（1.44 版）。**聚合模块的性能层跟踪改为随模型代数清空：上下文评分带来的模型代数一改变，就在该时刻清空确认状态、确认起点、幅度与确认后的元素。进行中的确认段记为「因模型切换而结束」，不触发命令，并在日界复核里写一条，类别为「性能层确认段因模型切换而结束」。单元测试为 `modelSwitchEndsTheConfirmationSegment`。
- **一级切换前验证（1.43 版设计补充，用户确认只记录）。**新、旧模型在各自标定集上的窗口误差中位数之比超过门槛（默认三倍）时，判为不该切换。每次一级切换都写一条日志，并在监测快照上记下比值与判定（`m3SwitchCheckRatio`、`m3SwitchCheckReject`）。作业参数 `--m3-switch-check-enforce` 默认为 false，即照常切换；取 true 时不通过就放弃这次重训，旧模型继续服务。门槛参数为 `--m3-switch-check-ratio`。单元测试为 `switchCheckRecordsAndOptionallyRejects`。
- **Python 参考实现的升级格**（1.44 版）安排在第二批收口之前完成，不阻塞全量重放。
