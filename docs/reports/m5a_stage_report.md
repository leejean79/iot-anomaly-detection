## 二、V-M5a-1（单元测试与核对）：通过

1. **单元测试**：`M5aCoreTest` 五个、`M5aPortTest` 一个，全量 139 个测试全部通过（沙箱 JDK 21；其中两个 MiniCluster 测试在 JDK 21
   上需要 `--add-opens`，JDK 11 以用户构建为准）。`M5aCoreTest` 用 Python 离线实现生成的合成数据：一台设备 13 天，跨 03-27 夏令时
   切换日，含标定日、缺轮日、守卫打标日与两段漂移，产生 6 次状态转移与 6 次爆发。
2. **Java 与 Python 逐条相同**：参照直方图、日记录、状态转移与爆发与 Python 相同。按 1.11 版裁定，只有光照经过变换的连续统计量
   （分位数、偏移、宽度倍数）用 1e−12 的容差，原因是 Java 的 `Math.log1p` 与 numpy 的 `log1p` 在约 2% 的整数输入上相差一个最低有效位；
   分箱 D、显著性、事件清单与状态转移逐位相同。在线算子（含中途检查点恢复、输出经 JSON 往返）与 Java 离线运行逐条相同；命令行的
   流式运行与逐台运行相同。
3. **分布检验与 scipy 一致**：显著性用极限分布（1.08 版），`m5a/stats.py` 的自检与 scipy 1.17.1 的 `kstwobign.sf` 相差小于 1e−12，
   卡方上尾与 `chi2.sf` 相差小于 1e−9 的相对误差；Java 的 `DayStats.ksP` 与 Python 的 `ks_p` 在对照数据上逐位相同。
4. **直方图近似的 D 误差**：离线实验中分箱 D 与精确 D 之差的中位数为 0.0002，最大 0.0527（C 03-29 光照，参照核查时为 0.0019）。超出
   「当日单箱最大质量与参照单箱质量 1/400 的较大者」这一界的设备日通道为 0 个。最大值超过一个箱宽（1/400），成因是夜间光照的并列值，
   1.09 版第三节已接受。

## 三、V-M5a-2（离线实验）：通过（1.09 版，按「测得、稳定、可归因」）

按运行前写定、1.07 版定稿的口径运行，九条口径逐条有数（`docs/reports/m5a_offline_report.md`）。按 1.09 版更正后的语义：剔除注入的
一遍共 245 次离群率爆发、459 次长记忆状态转移（平均每台每通道 11.5 次）。两处预期落空已由 1.09 版归因并更正语义：第一处是离群率零确认，
归因于爆发被一小时窗长封顶，改为「爆发」事件；第二处是平稳日上的长记忆事件，归因于平稳日参照与标定周参照不一致，改为状态转移。
三种统计方案在本数据段无法分辨，第五项验证推迟到重新冻结参照之后。对裁决中两句事实陈述的核对见事实摘要第五节，1.10 版已据此更正。

数据来自打开数据层那次短重放的 TaskManager 日志与两次运行的检查点体积采样（`docs/m5a/verify/perf.md`）。

| 项目 | 实测 |
| --- | --- |
| 日界处理耗时（一台设备关闭一个当地日，含五个通道的排序与检验） | 48 次（八台乘六个当地日，含不做检验的标定日）；中位数 2.2 毫秒，最大 46.1 毫秒。超过 10 毫秒的三次（G 30.2、B 35.9、F 46.1 毫秒）都在 03-26，即各设备第一次关闭可判日、第一次做检验；同日其余五台为 3.6 至 4.2 毫秒，之后各日都不超过 3.6 毫秒 |

| 每台的状态：日界关闭后（参照直方图、检测器窗口、未发出的爆发；Java 序列化） | 中位数 80,719 字节，最大 82,487 字节 |
| 每台的状态：日界之前的峰值（估计，加上当日读数乘八字节） | 中位数 412,779 字节，最大 427,327 字节 |
| 数据层算子的检查点体积 | 最小 26,896 字节（尚无参照时），日界之后回到 587,201 字节；日内随当日缓冲增长，按 0.59、0.91、1.57、2.88、4.85 MB 的台阶上升，最大 5.50 MB |
| 整次检查点合计 | 收尾时打开 17.066 MB、关闭 16.479 MB，相差 0.587 MB；最大值打开 23.567 MB、关闭 17.007 MB |

检查点体积的台阶来自当日缓冲的容量：缓冲从 1,024 个双精度数起按倍数扩容，检查点按容量整体序列化。每通道一天约 8,600 个读数，扩容到
16,384，所以日末的检查点体积约为实际读数所需的两倍：八台乘五个通道乘 16,384 乘 8 字节约 5.2 MB，加上日界之后的 0.59 MB 底数，与实测
的 5.50 MB 相符。按实际读数计算的峰值约为 3.4 MB。交接文档没有给性能门槛；是否需要改动见第九节第 1 条。

## 七、短重放中观察到的事实（只报事实）

1. **E 的温度阶跃注入没有引起 E 的离群率爆发**：注入时段（03-28 00:00 至 12:00 UTC）内与随后两天 E 都没有爆发，E 在短重放中唯一的一次爆发在 03-30
   20:20。E 的温度在 03-28 当地日结束时进入偏离。离线实验中十四段注入有 8 段出现离群率候选（事实摘要第二节第 6 条）。
2. **03-30 20:20 UTC 的同时爆发**：短重放中 A 至 G 七台在同一个十分钟（03-30 20:20）发生爆发，大小 9 至 10 轮，峰值 0.2 至 0.22。
   离线实验（标定周参照、全量数据）在同一个十分钟也有六台爆发（A、B、C、E、F、H），大小与峰值相近。两次运行的上游标定不同（预热一天
   与七天），这个十分钟仍然同时出现爆发。成因未查，按数据出处优先约定，如需要可按「出处材料、按当地时间的逐日剖面」的顺序核查。

## 八、过程中修正的问题

- `DeviceRound` 的参照直方图起初被插在一个 `@JsonIgnore` 注解与它所属的方法之间，导致参照直方图写不进 m1-out、而 `guardRunStartTs`
  被写出；上集群前已发现并改正，加了 JSON 往返测试。
- `M5aPortTest` 的对照数据被 `.gitignore` 的 `*.csv` 规则挡在仓库之外，在全新克隆上该测试会失败；已强制加入仓库。
- Java 离线运行器改为按文件顺序流式运行，避免在 jobmanager 容器里把约五十万条轮读进内存。
- `m5b/drift_json_to_csv.py` 只取性能层事件（漂移主题现在同时有数据层事件）。

## 九、需要设计会话裁定的事项

1. **检查点里的当日缓冲是否按实际读数序列化**：现状下日末的数据层检查点约 5.5 MB，其中约一半是扩容留下的空位，整次检查点最大值从
   17.0 MB 增至 23.6 MB。可选做法有三种：
   - 甲，维持现状，作为已知性能特征记录；
   - 乙，序列化时只写已用部分，改动只在 `M5aCore` 的序列化，算法不变；
   - 丙，把当日缓冲改成 Flink 的列表状态，改动较大。

   乙或丙都要重跑一次单元测试与短重放核对。我的建议是乙。
2. **M5a 阶段是否可以收口**：验收项一至五都已有结果；以上第 1 条的选择不影响等值结论。
