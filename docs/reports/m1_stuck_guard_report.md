# 重复值游程守卫：实现、阈值标定与离线核对

版本：2026-10-12。依据开发决策第十条（2026-10-09 裁决第二节第 1 条，设计会话 10-10 答复确认不变）。

## 一、结论

1. 守卫已实现并通过单元测试：逐设备逐检测通道统计连续完全相同原始读数的游程，达到阈值即在轮上打标，并计入
   监测快照（`stuckRounds`、`stuckChannelsMask`）。守卫只打标与计数，不改变两个检测通道的行为。
2. 阈值按全数据覆盖期（2022-02-11 至 07-25）各设备各通道自然最长游程的 2 倍取定。
3. **预言成立（离线）**：三次温度卡死注入都在开始后第 91 至 92 轮（约 15 分钟）被标记，即在一个阈值游程（E 的
   温度阈值 92 轮）之内；自然数据中游程达到阈值的次数为 0（阈值取自然最长游程的两倍，按构造如此）。在线的
   「自然数据零误触」要到下一次带阈值的重放才能实测。
4. 两个通道的阈值实际上使守卫失效，请设计会话知悉（第四节）：气体通道的自然最长游程来自读数停在 400 的时段，
   阈值 480 至 2,084 轮（1.3 至 5.8 小时），两小时的气体卡死在多数设备上不会被标记；光照通道夜间长时间不变，
   阈值 6,846 至 18,070 轮（19 至 50 小时），光照卡死基本不可能被标记。

## 二、实现

| 位置 | 内容 |
| --- | --- |
| `src/main/java/com/leejean/m1/RepeatRunGuard.java` | 阈值表解析与游程计数规则 |
| `RawCacheFunction` | 按设备号查阈值、更新游程、在轮上写 `stuckMask`；指标 `m1_guard_stuck_runs`（新出现的卡死游程数）、`m1_guard_stuck_rounds`（被打标的轮数） |
| `DeviceRound` | 新增 `stuckMask`（五个通道） |
| `MonitoringAggregator`、`MonitoringSnapshot` | 每 60 秒快照新增 `stuckRounds`（本窗口被打标的轮数）与 `stuckChannelsMask`（通道位图） |
| `M1Job`、`M2Job` | 参数 `--stuck-run-thresholds`，启动横幅打印 `Stuck guard:` |
| `syn-submit-m2.sh`、`env.example` | 从 `.env` 的 `SYN_STUCK_RUN_THRESHOLDS` 传入；留空则守卫关闭 |
| `RepeatRunGuardTest` | 6 个用例：解析、计数规则、缺失与冷启动、算子打标、快照计数 |

计数规则：比较原始值（逐位相等）；本轮缺失的通道既不延长也不打断游程；设备冷启动（缺席超过 1,000 × 10 秒）
时全部游程清零；阈值为 0 的通道不设守卫。离线脚本 `eda/repeat_run_lengths.py` 用同一套规则。

## 四、需要设计会话知悉的两点

1. **气体通道的最长游程来自「读数停在 400」。** 八台设备的气体最长游程都出现在读数等于 400 的时段，其中 B、C、
   E、F、G 五台同时始于 2022-05-09 08:55，持续 0.7 至 1.3 小时；A 在 05-10，D 在 03-23 13:18（三月事件开始的那一天），
   H 在 07-14（1.1 小时）。
   400 很可能是气体传感器输出的下限（例如二氧化碳当量的最低值），全机队同时停在下限，更像传感器重启或环境本身
   处在下限，而不是某一台卡死。按「两倍自然最长游程」取阈值，气体两小时卡死（约 720 轮）在 A、B、D、E、F、H 六台上
   不会被标记，只有 C（480）与 G（500）会。可选做法之一是在计算自然游程时排除下限值 400，由设计会话决定。
2. **光照通道夜间长时间不变。** 光照最长游程是夜间 0 至 10 勒克斯持续 8 至 15 小时，阈值折合 19 至 50 小时，光照
   卡死基本不可能被标记。这是光照数据本身的特点，按现行规则无法用游程识别。

## 七、2026-10-12 裁决后的改动：区分底值游程与普通游程

依据 2026-10-12 裁决书《上下文异常检测模块验收报告的两项待决事项》第二节。

### 7.1 规则

- **底值集合**：对每个检测通道，在八台设备合并的直方图里，取落在量程两端、且单个取值占比超过 1% 的取值。「量程两端」
  的操作定义由我补上：取值落在该通道观测范围最小值或最大值附近 5% 的区间内（`--floor-edge 0.05`）。预计温度、湿度、
  气压为空集。底值集合写入配置 `SYN_STUCK_FLOOR_VALUES`，由设计会话在本报告里核对后冻结。
- **普通游程**（读数不在底值集合里）：达到阈值即打标为「疑似卡死」（`stuckMask`），计入 `m1_guard_stuck_runs` 与监测
  快照的 `stuckRounds`、`stuckChannelsMask`。
- **底值游程**（读数在底值集合里）：设备层面只计数、不打标——达到阈值时写 `floorMask`，计入 `m1_guard_floor_runs` 与
  监测快照的 `floorRounds`、`floorChannelsMask`。「底值卡死」的判别归聚合模块（M5b）跨设备交叉核对。
- **监测信号**：两类游程格式一致。每 60 秒的监测快照给出本窗口最后一轮的 `guardRunLength`（五个通道的游程长度，未达
  阈值的通道为 0）与 `guardRunStartTs`（游程起始轮的时间戳）。这两项只进监测快照，不写进 `synergia-m1-out`。
- **阈值**：只用普通游程定阈值，等于干净参照段上普通游程自然最长值的两倍。

### 7.2 「干净参照段」的理解

我把它理解为「全数据覆盖期去掉拷贝段」：2022-02-11 至 07-25，排除 2022-06-12 23:00 至 06-20 00:00（数据事实第二十九条：
六月中旬一周是平移十四天的近似拷贝，按非数据处理）。若设计会话的本意是参照期 03-08 至 03-17（模型训练所用的九天），
请告知；只需把脚本的 `--start`、`--end` 改为该时段重跑，但九天内的自然最长游程会明显短于全期，阈值随之变小，在其余
日子上误触的风险更大。

**需要设计会话知悉的两点：**

1. **按裁决规则，底值集合只解决了 E、F 两台的光照。** 各台夜间的光照底值并不相同：E、F 停在 0 至 4，落在底值集合里，
   夜间游程改为底值游程，普通游程阈值降到 228 与 262 轮（约 40 分钟），光照卡死变得可以识别；A、G 夜间停在 10，C 停在 9，
   B 停在 5，D 停在 22，这些取值在八台合并的直方图中各自不到 1%，不进底值集合，夜间游程仍是普通游程，光照阈值仍为
   14 至 27 小时。若按设备分别取底值（每台设备自己的直方图），这五台的夜间底值也会被识别，但这偏离了裁决「该通道全集
   直方图」的写法，需要设计会话决定。
2. **气体的底值集合为空。** 400 在合并直方图中的占比不到 1%，按规则不算底值，气体的阈值保持 480 至 2,084 轮
   （1.3 至 5.8 小时），两小时的气体卡死在 A、B、D、E、F、H 六台上仍不会被标记。

### 7.4 待办
- 守卫上线后的第一次重放（随补遗四之后的全量重放进行）核对三件事：三次温度卡死注入都在阈值长度处打标；光照通道在

## 八、2026-10-13 裁决后的改动（开发设计日志 0.76 版，最小范围）

依据 2026-10-13 裁决书第四节与设计会话同日的工作量处置：守卫按最小范围继续，从上下文异常检测模块收口的关键路径上
摘下来——模块收口与补遗四（把 M3 训练移出任务线程）的发出不等守卫报告；在线核对搭补遗四之后的全量重放，只核对三次
温度卡死注入是否在阈值长度处打标；跨设备的「底值卡死」判别推迟到聚合模块（M5b），数据接入模块现在只发出底值游程的
计数信号；十大游程表只登记、不阻塞。

### 8.1 改动

| 项目 | 改动 |
| --- | --- |
| 底值集合 | 改为逐设备逐通道统计：取值落在该台该通道干净段实测范围两端各 5% 之内，且单个取值占该台该通道记录数超过 1%。配置格式改为 `A.Light=0/1,B.Light=5`。逐设备统计后仍为空集的通道（例如气体若无饱和底值）只走普通游程规则 |
| 缺口断开 | 相邻两条读数相隔超过 60 秒（探索性分析的缺口定义）即断开游程，离线统计与在线守卫一致（`RepeatRunGuard.GAP_SEC`） |
| 十大游程表 | 离线脚本逐设备逐通道列出最长的十个普通游程（起始时刻、长度、读数值），写入 `top10_runs.csv`；第一名超过第二名三倍且读数不在底值集合里时标为真实卡死候选，不参与阈值推导，阈值取剩余普通游程最大值的两倍 |
| 测试 | `RepeatRunGuardTest` 9 个用例（新增逐设备底值解析、60 秒缺口断开），全量 122 个用例通过 |

### 8.2 止损规则的执行情况

设计会话要求：若守卫与质量掩码的集成牵动下游接口，立即停下，把守卫整体登记为后期开发事项。本轮核对：守卫只在
`DeviceRound` 与监测快照上新增字段（`stuckMask`、`floorMask` 写入 `synergia-m1-out`；游程长度与起始时刻只进监测快照），
下游的点通道、上下文通道、重放核验、离线探针都不读取这些字段，读取 `DeviceRound` 的三个离线工具对新字段向前兼容。没有
牵动下游接口，未触发止损。
