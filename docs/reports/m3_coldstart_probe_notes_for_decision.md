# 冷启动检查点裁决的落实情况，以及需要设计会话知道的两处出入（2026-09-30）

- **依据**：2026-09-30 设计会话对冷启动检查点问题的裁决（原则重述、具体数字、前置要求步骤 C、三月运行
  中要记录的三项）。
- **提交范围**：`dev-claude` 分支。
- **结论**：配置与步骤 C 的工具已按裁决落实。另有两处事实与裁决中的推算前提不一致，它们不妨碍先做步骤 C，
  但会影响「六十分钟应被替换成多少」这个数字的得出方式，请设计会话知情并确认。

---

## 1. 已落实的内容

1. **检查点配置。** 作业新增参数 `--checkpoint-timeout-min`，默认值 10 即 Flink 默认值，其他运行的行为
   不变。步骤 C 与三月重放的提交命令显式传入 `--checkpoint-ms 30000 --checkpoint-timeout-min 60
   --checkpoint-tolerable-failures 3`，不再使用「容忍一百次」。
2. **步骤 C 的入口。** 包级可见的构造函数在 `com.leejean.m3` 包里，而联合作业 `M2Job` 在
   `com.leejean.m2` 包里，调用不到它。因此我把这个构造函数改为 public，并给作业加了参数
   `--m3-rounds-per-day`（默认 8,640）。传入非默认值时，作业启动横幅打印
   `COLD-START PROBE MODE … never use for acceptance`。生产与验收运行都不传这个参数。
3. **子任务编号进日志。** 「entering TRAINING」一行现在带上子任务编号，用来核对下面第 2 节的分布。
4. **TaskManager 单线程。** 用户已确认。worker 的 compose 文件给 taskmanager 加了 `OMP_NUM_THREADS=1`，
   只重建 taskmanager 容器；复位脚本的核对表新增了「TM 单线程」一项。
5. **记录工具。**
   - `syn-m3-coldstart-watch.sh` 每 15 秒记录检查点的挂起时长、完成与失败计数以及重启次数，
     用来回答「训练期间挂起的检查点在训练结束后是否正常完成」。
   - `m3_coldstart_report.py` 输出逐设备的训练墙钟时长与轮数、逐子任务的线程占用跨度、检查点小结，
     以及步骤 C 的全尺寸外推或三月运行相对离线的减速比。
6. **步骤 C 的操作手册。** 见 `docs/m3_coldstart_probe_runbook_zh.md`：重放 03-01 至 03-04，倍速 600，
   M1 标定缩为 1 天，每天折合 864 轮，其余参数与三月相同。这同时是 M3 的第一次在线打分
   （实验手册阶段二的类型 A）。

## 2. 出入一：设备并不是各占一个子任务，最慢的是一个串行训练三台设备的子任务

裁决的六十分钟推算假设「四台设备在同一个任务管理器上同时训练，各占一核」。但 M3 算子按设备分键，
设备到子任务的分配由键的哈希决定。我用 Flink 1.13.6 自带的 `KeyGroupRangeAssignment` 计算了并行度 8、
最大并行度 128 下的分配：

| 子任务 | 设备 |
| --- | --- |
| 1 | B、C、E |
| 7 | D、G |
| 2、5、6 | H、F、A（各一台） |
| 0、3、4 | 无 |

这个分配是确定的，步骤 C、三月重放与生产环境都一样。由此可以推出两点：

- **子任务 1 的任务线程要依次训练 B、C、E 三台设备。** 同一时刻最多只有 5 个线程在训练。对检查点来说，
  决定挂起时长的是「最慢的子任务」，也就是三台训练时长之和，而不是「最慢的设备」。
- **整个作业在这段时间里停止推进。** 子任务 1 被占住后，它的输入缓冲写满，上游的点异常算子因反压停住，
  检查点屏障也就到不了其他子任务。

用六月段离线网格的实测值估算（主节点，单线程，隐藏层 60，窗口 60，无争用）：C 为 922 秒（111 轮），
E 为 611 秒（74 轮），B 没有测过。只算 C 与 E 就已经 25.6 分钟；如果 B 与 C 相当，子任务 1 约为
41 分钟。再按裁决「取两倍」的做法，就是 80 分钟以上，超过了六十分钟。

## 3. 出入二：步骤 C 缩小的是数据量，它的实测时长不能直接当作全尺寸时长

裁决写道：步骤 C「产出的最慢设备的实际冷启动时长，就是第一节那个六十分钟该被替换成的实测值」。
但把每天折合轮数缩小到十分之一，训练窗口数也同比缩小（约 100 个，全尺寸约 1,000 个）。所以步骤 C
的训练时长大约只有全尺寸的十分之一，收敛所需的轮数也不同：每轮只有 2 次更新，耐心 20 轮只对应
40 次更新，而全尺寸是 320 次。

步骤 C 能测到、而且能迁移到全尺寸的，是在真实并发与真实子任务分配下的每轮耗时。报告脚本据此外推：

- 全尺寸每轮秒数取步骤 C 的实测值乘以 10。批次数按向上取整增长，每批另有固定开销，因此这样外推偏保守。
- 全尺寸轮数：离线测过的设备（C、E、G）用实测值；没测过的设备分别按「已测最多的轮数」与「上限 300 轮」
  给出下界与上界。
- 最后按子任务求和，取最慢子任务的两倍，作为超时的建议值。

**请设计会话确认**：是否接受用这个外推值替换六十分钟，并由三月运行的实测值加以核对。如果要求在三月
之前就得到一个直接测量的全尺寸时长，唯一的办法是做一次全尺寸冷启动：重放 7 天标定加 11 天收集，
约 43 分钟重放再加训练，这在内容上几乎就是三月运行本身。

## 4. 一处语义说明：容忍 3 次加超时 60 分钟，实际的重启线约为 4 小时

我从 Flink 1.13.6 的字节码（`CheckpointFailureManager.checkFailureCounter`）核对过：

- 计入「连续失败」的原因只有三种：超时过期、被任务拒绝、异步阶段异常。
- 任何一次成功都会把计数清零。
- 计数超过容忍值时作业失败。

对冷启动来说，这意味着：

- **训练短于 60 分钟**：挂起的检查点在训练结束后正常完成，这正是裁决要的效果。
- **训练长于 60 分钟**：会出现一次可见的超时失败，下一次检查点在训练结束后完成，计数清零，作业不重启。
  作业只有在连续第 4 次失败时才重启，而被阻塞的作业每次失败都要等满 60 分钟，所以阻塞约 4 小时才会
  触发重启。
- **九月十八日那类帧大小越限**：它在日志里的表现是 `Decline checkpoint … exceeds the maximum akka
  framesize`，属于「被任务拒绝」，立即失败而不是等到超时。在新配置下，每 30 秒一次，连续 4 次后重启，
  约两分钟内就能看到。裁决「让真正的失败仍然能被看见」的目的对这类故障成立。
- **会被推迟暴露的失败**：需要等到超时才暴露的失败（例如确认消息丢失），在新配置下要 60 分钟才会出现
  第一次失败记录。这是放宽超时本身的代价，如实记录在此。

## 5. 三月运行中的记录

裁决第三节要求记录三项，都已纳入三月手册与报告脚本：

1. **逐台设备的冷启动墙钟时长与实际轮数。** 来自「trained」日志行，报告第一节。
2. **并行训练相对单台离线的减速比。** 用三月数据上的离线参照（E、G、C）按每轮秒数相比，报告第四节。
   离线参照在主节点上运行，在线训练在 worker 上运行，两者 CPU 不同，所以这个比值同时包含机器差异与
   并行争用，两者无法分开，除非另在 worker 上跑一次离线参照。
3. **训练期间挂起的检查点在训练结束后是否正常完成。** 来自检查点时间线，报告第三节。

## 6. 用户决定：三月的注入与不注入分开跑（请设计会话知情）

2026-09-28 裁决书第三节安排一次三月重放同时承载 V-M3-4、V-M3-5、V-M3-6 与等值核验。2026-09-30 用户
决定按实验手册原来的类型 A、类型 B 分开跑：

- **第一次运行（类型 A，不注入）** 承载 V-M3-4 误报率、V-M3-6 性能与等值核验、点异常通道探针等值核验
  （挂账项）和逐子任务检查点峰值。
- **第二次运行（类型 B，注入）** 只承载 V-M3-5 注入召回。

这样做有三点后果：

1. 原先三月手册 0.4 所述的冲突不复存在。第一次运行里设备 E 没有注入，八台设备都能参与点异常通道的 ±1%
   比较。
2. 第二次运行要再做一次全尺寸冷启动，多花一次重放、训练与追赶的时间。
3. 两次运行在 03-26 之前的数据完全相同，训练出的模型应当一致。手册 B6 用「trained」日志行逐字比较来核对
   这一点。如果不一致，V-M3-5 仍在第二次运行自己的模型上评估，但这说明在线训练不能逐位复现，届时再上报。

注入方案（通道、强度单位、持续时间与排期）仍需设计会话在第二次运行之前确认，见三月手册 0.3。
