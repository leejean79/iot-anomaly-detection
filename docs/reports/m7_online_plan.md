# 聚合模块在线算子（M7DecisionOperator）与短重放等值的实现方案（2026-10-31）

依据：交接文档 `handover_m7_decision_stage_zh.md` 1.25 版第六节（在线算子）与第八节验收项三至五（短重放等值、时延表、性能），
以及 1.27 版裁决「下一步」。本文写明在线算子每一路输入在作业里从哪里来、与离线输入表的哪一列对应、在节拍时刻是否已经到达，
以及短重放等值的核对办法。

**结论**：
- 决策函数需要的全部输入都能从作业里已有的流得到，不需要改动五个已收口模块的任何判定逻辑与输出。
- 核对办法沿用数据层阶段验收项三（`syn-m5a-verify.sh`，即数据层短重放等值）的做法。

本文没有待裁决事项，按此实现；如果设计会话对第三节的核对办法有不同要求，请在验收前告知。

## 一、输入的来源与到达时刻

| 离线输入（`docs/m7/inputs`） | 在线来源（`M2Job` 中已有的流） | 节拍时刻是否已到达 |
| --- | --- | --- |
| 小时轮数、守卫打标轮数 | 标准化轮流（`RobustScaler` 之后的 `cached`）：每轮计一，守卫标志随轮携带 | 轮的事件时间即轮时刻，小时节拍在小时终点后六十秒触发，已到达 |
| 入口轮数 | 同一路轮流，按 `M2Gate` 的同一判据（冻结之后五个通道都有读数）计数 | 同上 |
| 冻结时刻、参照的 P10 与 P90 | 冻结后的第一条轮携带的参照直方图（`DeviceRound.getRefHistograms()`；`RefHistogram` 自带 P10、中位数、P90） | 冻结时即到达 |
| 温度、气体、光照的变换域小时读数数与和 | 同一路轮流，冻结之后的轮按 `ChannelTransform` 变换（光照为 log1p，删失与缺失不计） | 同小时轮数 |
| 到达滑动步的点通道离群轮数 | 点通道评分流（`scored`，`ScoreEvent`）：离群且轮时刻落在窗口末前六十秒之内，按轮去重 | 评分以窗口末为事件时间，已到达 |
| 上下文窗口数、超阈数、主分最大值 | 上下文评分流（`M3ScoreRecord`）：窗口末落在本小时内 | 评分以窗口末为事件时间，已到达 |
| 性能层元素 | 上下文评分流本身：十分钟粒度下，每条评分记录的主分就是性能层的一个元素（`M5bFunction` 在十分钟粒度下逐条喂入，不分桶） | 同上 |
| 性能层候选、确认、撤销 | 性能层事件流（`M5b-OPTWIN` 的输出），随元素到达立即发出 | 同上 |
| 数据层日结论（可判、日末偏离、转移） | 数据层的日记录侧输出（`m5aEvaluable`、`m5aDeviated`）与状态转移事件（DEVIATE、RECOVER），在日界的定时器上发出 | 日节拍在日界后六十秒触发，已到达 |
| 离群率爆发（报警元素、发出时刻） | 数据层事件流中的 BURST；`ts` 为报警元素，发出时刻取记录的事件时间戳 | 按 1.22 版第一点，只用小时终点前已发出的爆发 |

**两点说明。**

1. **上下文评分的事件时间。** 上下文评分在补遗四（把 M3 训练移出任务线程）之后可能晚于窗口末发出，但下游水位线不会越过尚未发出的评分（性能层依赖同一性质）。所以在线算子在节拍时刻看到的评分，与离线按窗口末取用的评分相同。短重放的逐条比较会直接检验这一点。
2. **小时均值的求和顺序。** 离线输入的变换域小时和由 Mac 上的提取脚本用 pandas 求和，在线逐轮累加，两者在最低位上可能有差别。小时均值只进入「同步变化」的门槛比较，不出现在日志里。短重放的比较不受影响，因为离线运行器读的是同一次短重放的转储，见第三节。

## 二、在线算子的结构

- **输入统一**：各路流先映射为同一种输入记录（类别加字段），再合并，按常量键分区。算子并行度为一，用键控状态与事件时间定时器。
- **输入整理器**：新增 `M7InputAssembler`，在线算子与离线运行器共用。它按设备累计当前小时的观测（轮数、入口轮数、守卫轮数、离群轮去重集、上下文计数与最大值、变换域和），并把事件转交 `FleetDecisionFunction`。
- **定时器**：第一条输入到达时，注册其所在小时的「终点加六十秒」定时器；每次触发时依次做下列事情：
  1. 做该小时的告警节拍；
  2. 若到了决策节拍，做决策节拍，日界时含复核；
  3. 注册下一小时的定时器，没有读数的小时也照常推进。
- **输出**：
  - 告警写 `synergia-alerts`，命令写 `synergia-adapt`，复核写 `synergia-alerts` 并标明类别；格式与离线三份日志的行相同。
  - 另写一份输入轨迹到 `synergia-m7-trace`，内容为每个节拍送入决策函数的小时观测与事件，供核对与排查。
- **参数**：交接文档第六节所列参数从作业参数读入。
  - p_point 取全量离线推导的值 0.061343306938749904，不在线推导，因为短重放不含平稳日参照期。
  - 本算子有总开关 `--m7-enabled`，默认关闭；关闭时作业拓扑与现在完全相同。
- **单元测试**：输入整理器对离线 `hours.csv` 的口径逐列核对。在线算子再用 Flink 的测试工具驱动一组合成流，检验定时器、日界与夏令时切换日。

## 三、短重放等值（验收项三）的核对办法

编排脚本 `deploy/scripts/syn-m7-verify.sh`，结构与 `syn-m5a-verify.sh` 相同：
- 在 master 的 tmux 会话里无人值守运行，子命令为 `start`、`status`、`fetch`、`stop`；
- 重放区间为 03-24 至 03-31，预热、标定日、M3 设置与倍速都与数据层的短重放相同；
- 跑两次，只有 `--m7-enabled` 不同。

核对四项：
1. **在线与离线逐条相同。** 在线算子的告警、命令、复核三份日志，与 Java 离线运行器在 on 运行的转储上算出的结果逐条相同。转储包括标准化轮、评分、漂移事件、日记录；离线运行器经同一个输入整理器读入转储。比较截止到最后一条轮之前六小时，理由同数据层。
2. **上游评分逐位相同。** on 与 off 两次运行的评分（点通道离群记录与上下文全部评分窗）逐位相同。
3. **上游其余输出逐位相同。** on 与 off 两次运行的标准化轮、漂移事件与日记录逐位相同。
4. **零级命令。** 指出区间内有无零级命令；没有时说明原因（参照取 03-25 标定日，G 光照在区间内只偏离一天）。

**预知的限制**：「现场条件」的日内基线要冻结后十个当地日才建成，短重放区间只有八天，所以这一规则在短重放上不会被实际检验（1.23 版裁决第四点），由单元测试与全量离线实验覆盖。

## 四、时延表与性能（验收项四、五）

**时延表**：三月事件、G 光照、气体抬高三段，从上游第一条信号到告警、到命令生效的时延。
- 在全量离线结果上计算，加上节拍的六十秒；
- 短重放上另以在线日志的处理时间核对节拍的实际触发延迟。

**性能**：取自 on 运行，包括算子状态大小、每个整点与日界的处理耗时（日志）、检查点体积增量（与 off 运行比较）。

## 五、实施顺序

1. 输入整理器与在线算子，加单元测试。
2. 离线转储运行器：读短重放的转储，经输入整理器驱动决策函数。全量运行的标准化轮转储不在库里，所以本地用合成转储做回归。
3. 作业接线（`--m7-enabled`）、topic 创建、jar 核对项。
4. 短重放编排脚本与核对脚本，交给用户在集群上执行。
5. 时延表与性能表。
