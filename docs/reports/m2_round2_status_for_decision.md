## 1. 已经确证的事实

下列各条都有实测数据或代码级依据，不是推断。

**其一，事件时间对齐缺陷已定位并修复。** `RoundAssembler` 从 `onTimer` 发射，而 Flink 给
`onTimer` 发出的记录盖的是**定时器**的时间戳（轮时间 + 30 秒关闭延迟），`M2Gate` 却按轮时间设
`arrival`。在 60 秒滑动步下，这使**约一半的轮从未进入 MCOD 状态**。修复（方案 A：在
`RoundAssembler` 之后重新对齐事件时间）已合入，并有三项测试覆盖：δ = 0 / 10 秒 / 30 秒 下每轮窗口
点数分别为 60 / 50 / 30，作业级测试断言下游时间戳等于标称轮时间。修复后窗口几何恢复到探针的
1.001 倍。

**其二，三月基线在 Java 11 上已经跑出一份干净结果。** 五条完整性断言全部通过：轮数 2,049,816 对
EDA 期望 2,047,283（+0.124%，容差 ±0.2%）；同设备同时间戳重复计数 **0**；边界对齐通过；八台设备
的标定冻结全部落在第 8 天；作业重启次数 **0**。三道闸对账精确闭合：
`admitted 1,565,797 = rounds 2,049,816 − warmup 483,840 − missing 179`。

**其三，checkpoint 阻塞项在干净环境下没有复现。** 43 次 checkpoint 全部 `COMPLETED`，为此加的
`--checkpoint-tolerable-failures` 兜底一次都没被触发。逐算子状态剖面已测出：`RobustScaler` 在标定
冻结前累积到 15.76 MB（八个子任务合计），冻结时塌回 0.045 MB；`Pmcod` 接手后在 10.1 至 16.58 MB
之间起伏，排空后稳定在 8.889 MB。

**其四，逐设备偏差的成因已经查清，且在探针一侧而非作业一侧。** 偏差是一个近似恒定的加性偏移：
A 到 G 七台一律低 0.0059 个百分点，H 为 0。把两侧的滑窗数与「比率之和」并列，两个不变量立刻显形：
探针**恰好**多 60 个滑窗（60 = W/S = 3600/60），多出来的部分贡献的比率之和**恰好约 2.00**
（实测 1.974 至 2.019）。这两个不变量与设备无关、与半径无关（R 取 0.75、1.0、1.5）、与离群密度
无关（各设备密度相差 20 倍）。

机制在 `M2Probe.java` 的循环上界里可以直接指认：修正前的条件 `windowEnd - windowMs <= maxArrival`
等价于 `windowStart <= maxArrival`，因此探针会一直滑到窗口起点越过最后一个数据点为止——在最后
一个点之后还要多走 W/S 步，这段里窗口只出不进、逐步排空；而运行中的 Flink 作业只触发
`windowEnd ≤ 水位线` 的窗口，流未结束时水位线停在最后一个事件上，这些排空窗口尚未触发。排空段里
点数跌到 k 以下时窗内全员离群、该滑窗离群率饱和为 1.0，而「逐滑窗比率的算术平均」对这类滑窗没有
任何加权保护。该机制已由 `ProbeDrainTailTest` 用真实的 `McodCore` 固化，循环上界已按裁决修正。

## 2. 仍未解决的事项

**其一，逐设备等值核验这道关卡从未真正通过过。** 它至今仍在拿作业（新口径）与
`docs/m2_probe_7d_clean.csv`（Java 8 运行时 + 旧口径）相比，因此必然带着那 0.0059 个百分点的偏移。

**其二，Java 8 参考表无法用新口径重算。** 本项目的 jar 自 Addendum 2 起是 Java 11 字节码
（class file major 55），在 JDK 8 上会直接 `UnsupportedClassVersionError`。为此新增了
`--legacy-drain-tail` 开关，把一次双变量比较拆成两次单变量比较（旧口径 J11 对 J8 参考 = 只变运行时；
新口径对旧口径 = 只变口径）。**这套方案只在单元测试的合成数据上验证过，从未在真实数据上跑通过。**

**其三，逐子任务 checkpoint 峰值未实测。** Flink 1.13 的 `/checkpoints/details/<id>` 响应不含
per-task summary，要再调 `/subtasks/<vertexId>`。目前记录的是八个子任务的**合计**，而
`akka.framesize` 限制的是单条确认 RPC。按并行度平均约为 1.97 与 2.07 MB，但这是「假设均匀」的下界
估计，不是实测。

**其四，首轮那条 26.1 MB 的确认 RPC 来源仍然未知。** 三个候选（蓄水池 2.31 MB、`Pmcod`、
`RoundAssembler`）已逐一实测排除。两轮之间同时变了三件事（对齐修复、checkpoint 间隔 10 秒改 30 秒、
环境重建），**一次观测无法分离三者的贡献**，因此「为什么不再复现」这个问题我不给机制解释。

**其五，交接文档授权的方案 E 与实测冲突，等待确认放弃。** 实测：装箱形态 2,419,220 字节，改成每轮
一条 `double[5]` 后是 2,661,124 字节，**反而大 10%**；而三月干净重跑测得 `RobustScaler` 峰值合计
15.76 MB，方案 E 针对的「蓄水池单子任务 26 MB」并不存在。蓄水池存储形态未动。

**其六，第 4 轮（设备 G 逐小时分布 v2）范围未定。** 现有 before/after 两份对应的是
`--relative-guard` 开关的两种配置，完整复现需要两次重放；仓库也没有记录这两份当初用的是哪个月份。

## 3. 这一周的代价构成（如实记录）

自 2026-09-12 起共 49 次提交。期间有四轮实验作废或白跑，成因分列如下：

| 轮次 | 成因 | 性质 |
| --- | --- | --- |

| 第二次 | 事件时间偏移缺陷，约一半的轮未入 MCOD | **产品缺陷**（已修复） |
| 第三次 | checkpoint 撞 `akka.framesize` → 作业重启 → 25,517 条重复轮 | 环境/平台 |

此外还有五处只在操作机上才暴露的脚本缺陷，各消耗一到两个来回但未浪费重放：heredoc 吞掉管道、

`lint-scripts.sh` 作为交付前静态检查，以及 `syn-reset-env.sh` 把环境复位做成可核对的固定流程。

**需要设计会话知情的一点**：上述四轮里，只有一轮的根因是产品缺陷，其余三轮分别来自配置漂移、平台
限制与我的命令错误。也就是说，这一周的时间**主要不是消耗在算法或模型问题上**。

## 4. 继续做完还需要什么

操作者已经清理了 topic 并开始跑六月段，因此三月数据不在集群上了。走完这道关卡需要**一次完整的
三月重放**（加速 3600 倍，墙钟约 20 到 60 分钟）外加三次探针与一次逐设备核验，合计约两小时，其中
大部分时间无需值守。

与前几轮不同的是，这一次的失败模式已经被逐个堵上：环境复位有核对表并以退出码为硬门槛；探针在
有效设备为 0 时退出码 3 且不再产出只有表头的假产物；转储条数默认值提到 3,000,000；断言五会抓住
任何作业重启；`syn-ckpt-watch.sh` 会留下逐算子状态曲线。

## 5. 我的建议

**建议再跑一次，但设定硬性的收敛条件，并且把 M3 与这道关卡解耦。** 理由与边界如下。

**支持再跑一次的理由**：这一次是**确认性**的，不是探索性的。偏差的 100% 已被一个代码级机制解释，
且该解释带着两个极强的不变量——恰好 60 个滑窗、恰好约 2.00 的比率之和，跨越 20 倍密度与三种半径
仍然成立。一个真实的运行时差异不会产生这种与密度无关的恒定加性偏移。所以预期结果是通过，而不是
再发现新问题。代价约两小时，其中大部分无需值守。

**必须预先约定的收敛条件**：两次单变量比较的三个数——旧口径 J11 对 J8 参考在 **±1%** 内、新口径对
旧口径 `slides` 恰好少 **60**、比率之和少约 **2.00**。**三个数同时成立就关闭这道关卡**；任何一个
不成立，**立即上报而不是就地迭代**。这一条是针对这一周的教训写的：前几轮的时间正是消耗在
「发现异常 → 就地再跑一轮 → 再发现异常」的循环里。

**建议解耦的理由**：迁移等值的实质证据其实已经具备（第 1 节其四的两个不变量）。逐设备核验的形式化
PASS 主要服务于验收记录，而不是服务于「M3 能不能开工」这个判断。如果 M3 的排期紧，可以在这次确认性
重跑进行的同时推进 M3 的设计与本地开发，不必等它。

**如果设计会话裁定不再跑**：那么需要一并裁定两件事。第一，`docs/m2_acceptance.md` 里逐设备等值这
一条如何结案——是记为「以机制解释结案、未取得形式化 PASS」，还是降级为非阻塞项。第二，
`docs/m2_probe_7d_clean.csv` 作为参考表的地位如何处置——它是旧口径的，继续用会让今后每一次核验都
带着这个偏移；建议至少在文件头加一条警示注释，说明它与修正后的探针口径不可直接比较。
