# 重放完整性核验在六月段上的结果与请求确认（2026-09-27）

## 摘要

2026-09-27 裁决书要求集群运行前先过重放完整性核验。M3 网格用的数据是六月段重放
（2022-05-29 至 2022-06-20，m1-out 共 1,103,663 条，与 2026-09-20 首次离线试跑的转储行数完全相同）。
而核验脚本是为三月整月写的，在六月段上**无法全部通过**：断言一缺少六月段的 EDA 参照；断言三、四
各有一处不符。逐条核对后，我认为这些不符都不涉及网格实际使用的数据，但门槛是设计会话定的规则，
是否接受由设计会话决定。**在确认之前，补跑照常进行，但选定的隐单元数不写入作业默认值。**

## 二、逐条分析

**第一，断言二通过，这是最重要的一条。** 重放最常见的损坏是重发造成的重复，本次为零。

**第二，断言四只有设备 H 不符，而且方向与该断言要抓的问题相反。** 这条断言的本意是抓压缩或重发，
那会使冻结**提前**到第 4 天左右。H 是**推迟**到第 16 天，说明它在前一周缺数据，只能更晚攒满 7 天
标定窗口。H 有单独停机的历史（`docs/m1_acceptance.md` 记录了它在 2022-05-21 至 05-23 的单独停机段），
因此这更像是设备自身的数据缺口，而不是重放损坏。**网格只用 C、E、G 三台设备，它们都恰在第 8 天冻结。**

**第三，断言三只有结束边界不符。** 数据最晚一轮是 2022-06-19T23:14:45Z。若重放的结束参数是
2022-06-20T00:00:00Z（不含），则比期望的最后一轮早 45 分 5 秒；若是 2022-06-21，则早约一天。
这可能是重放提前停止，也可能是原始数据在这里自然结束，仅凭核验输出无法区分。

但这段缺口不在网格用到的数据里。网格对每台设备跳过 7 天预热，再取 7 天训练、2 天早停，共 16 天，
即大约用到 2022-06-14。汇总 CSV 的窗口数与此精确吻合（例如 C 在窗口 60 下训练 991 窗加剔除 17 窗
共 1008 窗，正好 7 天；早停 288 窗，正好 2 天）。

## 五、补查结果（2026-09-28，按 2026-09-27 裁决书第三节）

### 5.1 断言一：有参照后通过

参照值由 `eda/count_rounds.py` 从原始 CSV 数出（3471 个数据文件，解析失败 0 个；统计口径为唯一的
「设备 + 时间戳」；窗口为 2022-05-29 至 2022-06-20，按 UTC，前含后不含）。EDA 已有的逐日表数的是
传感器行数，不是轮数，因此另写了这个脚本；它用的是与 EDA 扫描相同的格式嗅探与解析参数。

| 项目 | 值 |
| --- | --- |
| 参照（原始数据） | 1,103,721 轮 |
| 实测（m1-out） | 1,103,663 轮 |
| 相对偏差 | −0.0053% |
| 容差 | ±0.2% |
| 结论 | **通过** |

逐设备逐日表：`docs/june_segment_eda_rounds.csv`。

### 5.2 结束边界：原始数据自然结束，重放没有提前停止

重放器日志（master 上 `/opt/fa-iforest/syn-replay.log`）记录的六月段运行：

| 项目 | 值 |
| --- | --- |
| 启动参数 | `--speedup 3600 --start 2022-05-29 --end 2022-06-20` |
| 已发送记录 | 8,829,448 |
| 发送失败 / 读文件失败 | 0 / 0 |
| 空闲压缩事件 | 1（即 102 小时的全场停机） |
| 退出码 | 0（2026-09-20 09:51:49） |

原始数据中 A 至 G 七台设备的最后一轮都在 2022-06-19 的 23:15:57 至 23:16:11 之间，彼此只差 14 秒，
比重放结束参数（06-20 零点）早约 44 分钟。重放以退出码 0 正常结束、没有任何发送失败，说明**原始
数据本身就在 06-19 23:16 前后结束**，重放没有提前停止。断言三的「最晚一轮」不符，是因为期望值取的
是名义右界（06-19 23:59:50，我此前按 06-21 推算时更是差了一天），与三月数据在月末有 80 秒自然缺口
属于同一类情况，只是这里缺口更长。

**一处尚未完全证实的推断。** m1-out 的最后一轮是 23:14:45，比原始数据的最后一轮早约 80 秒；参照与
实测之差 58 轮，也正好约等于 7 台设备各少 8 轮左右（10 秒一轮，约 80 秒）。这与 M1 的 55 秒有界乱序
水位线在数据流末端的效应相符：最后一批事件之后没有更晚的事件推进水位线，末尾几十秒的轮就不会被
输出。这个解释与数据的量级一致，但我没有逐台核对 m1-out 的最后时间戳；它影响的只是数据流末尾
约 80 秒，不在网格使用的数据范围内。

设备 H 的原始数据在 2022-06-13 16:52:30 就结束了，全段只有 63,198 轮，与它第 16 天才冻结一致。

### 5.4 登记时发现的一处疑点（2026-09-28）

逐日轮数表（`docs/june_segment_eda_rounds.csv`）显示，8 台设备 06-13 至 06-18 的轮数与 05-30 至 06-04
**逐日完全相等**，06-19 恰为 06-05 减去 262 或 263 轮。这提示原始数据在停机之后的一周可能是停机之前
数据平移 14 天的拷贝。核查脚本 `eda/check_shift_copy.py` 已写好并用合成数据验证过，待在原始数据上
运行。结果出来之前，这只是一个疑点，不是结论；它对 M3 网格的选型结论（三台设备受同样影响）与
六月段核验的通过都没有影响，但若属实，会影响对 DF-12 恢复浪涌分析中「七台设备同一秒恢复」的解读。

**2026-09-28 核查进展。** 在原始数据上比较了 06-13 起 7 天与 05-30 起 7 天（平移 14 天）：时间戳对上
100%（3,441,488 行，含设备 B 不规则的缺轮模式），数值相同 52.22%。时间骨架几乎可以肯定来自较早
一周；数值不是逐行拷贝，但 52% 是否高于自然水平，要等逐传感器分解与对照平移的结果。脚本第一次
运行时打印的结论「采样时刻重合，内容不是拷贝」下得过早，已改为不自动下结论。

**2026-09-28 结论。** 逐传感器分解与对照平移表明，停机后一周是停机前一周平移 14 天的近似拷贝：连续
通道相关系数全部为 1.000，对照组为 0.15 至 0.84，时间戳对上 100% 对 11.90%。独立报告见
`docs/reports/data_june_shifted_copy_for_decision.md`。
