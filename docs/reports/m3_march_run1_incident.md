## 2. 推断（未经证实）

**作业从 REST 上消失而不是变为 FAILED，最可能的原因是 JobManager 进程重启。** 本集群没有高可用配置，
JobManager 重启后作业不会恢复。

**最可疑的原因是 JobManager 堆内存不足。**

- 本集群用 JobManagerCheckpointStorage，所有检查点状态都保存在 JobManager 的 Java 堆里。
- `JM_HEAP_MB=1024` 是整个进程的大小，扣除元空间与 JVM 开销后，堆只有约 0.5 GB。
- 第 16 至 19 号检查点如果在 JobManager 里仍被引用，每个约 40 MB，四个约 160 MB；第 20 号随各子任务训练
  完毕陆续确认，又在增长；完成检查点时序列化元数据还会再复制一份。这些加起来足以把约 0.5 GB 的堆推向
  上限。

步骤 C 的状态只有几 MB，所以只出现一次统计悬挂，没有拖垮 JobManager。这一推断需要诊断结果中的以下证据
来证实或推翻：

- JobManager 容器的重启次数，以及是否因内存被杀；
- JobManager 日志里的 `OutOfMemoryError`；
- 第 16 号检查点前后的日志；
- 集群配置中的最大并发检查点数。

## 3. 诊断脚本收集的内容

`syn-m3-diag.sh` 只读，不改动任何东西。它收集以下内容：

- 三台机器上相关容器的状态：启动时间、重启次数、是否因内存被杀；
- JobManager 与两台 TaskManager 自日志起点以来的完整日志；
- 集群配置与作业列表；
- 三台机器的内存情况。

它还会从日志中摘出检查点、作业状态变化、异常与 M3 训练记录，写入 `diag_summary.txt`。
